# Граф вызовов context-chunks-mcp ↔ llm-ladder: ТЗ интеграции

Статус: ТЗ на исполнение, ревизия 2 (владелец перерисовал граф). Цифры — замеры
2026-10-08 на проде; код прокси дорабатывается в `trained-assist/context-chunks-mcp`
(его здесь не трогаем).

Компаньон: [spec-compression-threshold-for-context-chunks-mcp.md](./spec-compression-threshold-for-context-chunks-mcp.md) —
**когда** сжимать (350 КБ базовый, 100 КБ перед платной). Здесь — **как строится граф вызовов**.

---

## 1. Два шага, и они разные по своей природе

| шаг | что делает | нужен ли LLM |
|---|---|---|
| **COMPRESS** | детерминированное сжатие входа (код/логи/веб/доки), кэш оригиналов, набор `ref`-ов | **нет** |
| **LLM-REF** | читает сжатое представление, отвечает в формате задачи **или** просит ref'ы | **да — через лестницу** |

COMPRESS выполняется **один раз** на вход и никогда не вызывает ни лестницу, ни LLM.
Всё, что дальше — это LLM-REF, и оба его шага (первый и повторный) идут **просто через
лестницу**: она сама выберет ступень, сама уйдёт вниз по отказам, сама вернёт формат
заказчика (JSON или текст).

## 2. Граф вызовов

```
клиент
  │  POST /v1/chat/completions, messages = P
  ▼
ПРОКСИ
  │
  ├─ sizeof(P) < порога ──────────────────────────────────────────────────────┐
  │     (350 КБ; 100 КБ если маршрут «перед платной»)                         │
  │     ВЫЗОВ L0 — лестница, model = <лестница клиента>, messages = P         │
  │        → ответ клиенту  [ТЕРМИНАЛ]                                        │
  │                                                                           │
  └─ sizeof(P) ≥ порога → COMPRESS(P) → C + ref'ы в кэш                       │
        │                                                                     │
        ▼                                                                     │
     ВЫЗОВ L1 — лестница, model = <лестница клиента>, messages = C,           │
                response_format = json_object                                 │
        │                                                                     │
        ├─ { "answer": … }                      → клиенту  [ТЕРМИНАЛ]         │
        ├─ сломанный / не-JSON                  → ВЫЗОВ Lfix (пин = winner(L1))
        └─ { "need_refs": [R1] }                                                  │
             │                                                                │
             ▼                                                                │
          ВЫЗОВ L2 — ПИН = winner(L1), messages = C + unpack(R1, ≤3 ref'ов)  │
             ├─ { "answer": … }                  → клиенту  [ТЕРМИНАЛ]         │
             └─ { "need_refs": [R2] }                                         │
                  │                                                           │
                  ▼                                                           │
               ВЫЗОВ L3 — ПИН = winner(L2), messages = C + R1 + unpack(R2)    │
                  ├─ { "answer": … }              → клиенту  [ТЕРМИНАЛ]        │
                  └─ иначе → вернуть лучший ответ/сжатый контекст + флаг      │
                                                                              │
     ВЫЗОВ Lfix — ПИН = winner, вход = ТОЛЬКО «переформатируй в JSON»        │
        (маленький: объём данных там резко меньше)                             │
```

Число обращений к лестнице на один вход клиента — **жёстко ≤ 4**: L1 + L2 + L3 + Lfix.
Это потолок, а не план; в типичном случае — **один** (L1 отвечает сразу).

## 3. Липкий пин: продолжаем с той ступени, которая ответила

Правило владельца: *«если дошли до платного шага, то уже от него — раз был перегруз,
то сейчас совсем будет перегруз»*.

Поэтому L2 / L3 / Lfix пинуются не на «какую-то дешёвую модель», а на **победителя
предыдущего вызова**:

| чем ответил предыдущий вызов | что делаем на следующем |
|---|---|
| бесплатный ранг (`opencode-go/*-free`, `zen-rings/*`, `openrouter/*:free`) | пин на него: экономим хоп обхода |
| **платный** ранг (`opencode-go/mimo-v2.6-flash` и дороже) | пин обязателен: бесплатный путь в этот момент перегружен/исчерпан, возврат к нему = задержка без результата |
| победитель неизвестен (ответ без `model`) | пин `opencode-go/mimo-v2.6-flash` — запасной вариант, он есть во всех не-фри лестницах |

Пин экономит не только время: каждый повторный обход с головы заново платит бюджет
`free_model_daily_requests` (лимит 1000/сутки, замерено 355/1000) и минутный лимит кольца
(50/мин на (репозиторий, модель)).

## 4. Правила, из-за которых граф не превращается в петлю

### 4.1 LLM-REF ходит на `LADDER_URL`, не на адрес прокси

Если повторный вызов пойдёт через прокси, COMPRESS применится к входу, который уже сжат
(к нему приплюсованы распакованные ref'ы) — получится петля без пользы. Проверка на
приёмке: во внутренних вызовах нет заголовка прокси, и прокси логирует ровно один
вход на клиентский запрос.

### 4.2 Пин обязан влезать по размеру — иначе лестница уходит в полный обход

Потолок `opencode-go/*` = **100 000 токенов ≈ 400 000 байт** (`bytes/4`, `src/size-policy.js`).
Ловушка в коде лестницы: при пине, который НЕ влезает, она **не отказывает**, а пропускает
его и продолжает обход по всем остальным ступеням (`src/ladder.js:712`: `fits()` → `continue`).
«Пин, который не влез» молча превращается в обход с головы — то, чего мы и избегаем.

Поэтому размер входа L2/L3 меряется **до** вызова
(`Buffer.byteLength(JSON.stringify(messages), 'utf8')`):

| вход | что делает прокси |
|---|---|
| ≤ 350 000 байт | пин победителя, как задумано |
| 350 000 … 900 000 байт | переключить пин на big-window ранг `openrouter/nvidia/nemotron-3-ultra-550b-a55b:free` (окно 1 000 000, есть во всех не-фри лестницах) |
| > 900 000 байт | **не распаковывать**: вернуть лучший ответ/сжатый контекст + флаг `truncated_refs`. Кусок на 15K символов не стоит того, чтобы ронять вызов в полный обход |

### 4.3 За раз распаковывать не более 3 ref'ов

Один ref = кусок до `MAX_CHUNK_SIZE` = 15 000 символов. Три — это ≤ 45K символов сверх C;
больше — вход L2 начинает упираться в потолок, а на промежуточных шагах экономия теряется.

### 4.4 Внутренние вызовы — не стрим

`stream: false` (TTFB-логика и синтез потока тут ни к чему), `max_tokens` по задаче
(переформат в JSON ≈ 2 000; распаковка ≈ 8 000), `ladder_timeout_ms` ≤ 30 000,
`ladder_total_timeout_ms` ≤ 60 000. Лестница сама клампит эти значения
(`src/handler.js`, `src/ladder.js`).

## 5. Контракт «мне нужны ref'ы»

LLM-REF — это свой промпт со своим форматом вывода (поэтому шаг и вынесен из COMPRESS).
Основной вызов L1 идёт с `response_format: { type: "json_object" }` — лестница прокидывает
его дальше, а на моделях, которые отвечают на это 400, сама снимает и повторяет
(`RF_400_RE`, `src/ladder.js`).

```json
{ "answer": null, "need_refs": ["<ref1>", "<ref2>"], "question": "короткий вопрос к себе" }
```

- `answer` непустой → терминал;
- `answer: null` + `need_refs` → распаковать ≤3 и сделать следующий LLM-REF;
- не-JSON → `Lfix` на том же пине, вход только с просьбой переформатировать.

## 6. Экономика шага

| вызов | вход | кто отвечает | стоимость |
|---|---|---|---|
| L0 (без сжатия) | P ≤ 350 КБ | бесплатный Go (`longcat-2.5-preview-free`), бенч **39/39**, 7–11 с | $0 (free, unlimited limited-time) |
| L1 (сжатый) | C ≈ 8 % от P | обычно то же | $0 |
| L2, L3 | C + ≤3×15K символов | **пин победителя** | по тарифу победителя |
| Lfix | только ответ | тот же пин | копейки |

При сжатии ~92 % (цифра владельца) даже три повторных вызова в **платный** пин дешевле
одного несжатого входа туда же: 1M несжатых токенов = $0.28 против ~80K сжатых × 3 ≈ $0.007.

Если предыдущий вызов ответил **бесплатным** рангом — повторный пин бесплатен; и это ещё
одна причина не возвращаться к обходу с головы.

## 7. Атрибуция и наблюдаемость

Каждый вызов прокси несёт `x-ladder-app: context-chunks-mcp` и `x-ladder-app-title`
(иначе в `/v1/analytics` трафик прокси смешивается с агентами, #136).

Логировать в прокси (нужно для бенча):

- размер входа и выхода каждого вызова (байты `JSON.stringify(messages)`);
- `model`-победитель каждого вызова — из него строится пин следующего;
- число `get_context` и сколько ref'ов распаковано;
- терминал (каким вызовом ответили) и причина, если дошли до потолка §4.2.

## 8. Открытые вопросы

1. ~~Что возвращать при отказе L2/L3?~~ **Решено владельцем**: идём по лестнице, то есть
   отказ L2 — это не финал, а повод для L3; финал — либо `answer`, либо лучшее, что есть,
   плюс флаг `truncated_refs`.
2. Нужен ли `Lfix` всегда, или только когда клиент явно ждёт JSON?
3. Кто хранит ref'ы при рестарте прокси: ин-мемори (сейчас) или Redis/D1? При рестарте
   распаковка вернёт «ref не найден» — тогда L2 должен получить явный маркер вместо тишины.
4. Порог «перед платной» (100 КБ) — только ко входу клиента или и ко входу L2/L3?
5. Если победитель L1 — zen-ранг (`zen-rings/*`): пиновать zen или сразу следующую по
   надёжности бесплатную ступень? Zen отвечает пустым телом в ~20 % жирных случаев.

## 9. Чеклист интеграции

1. COMPRESS не вызывает ни лестницу, ни LLM; LLM-REF вызывает только `LADDER_URL` (§4.1).
2. L2/L3/Lfix пинуются на победителя предыдущего вызова; без победителя — на
   `opencode-go/mimo-v2.6-flash` (§3).
3. Размер входа L2/L3 меряется до вызова: ≤350 КБ → пин; ≤900 КБ → пин big-window ранга;
   >900 КБ → без распаковки (§4.2).
4. Потолок обращений — 4; каждый путь ведёт к терминалу (§2).
5. Не более 3 ref'ов за раз (§4.3).
6. `x-ladder-app: context-chunks-mcp` на всех вызовах (§7).
7. Прогон A/B/C/D бенча + отдельный замер: сколько `get_context` на вызов (цель 0–2),
   доля вызовов, дошедших до L3, и доля вызовов, ушедших в платный пин.
