# Граф вызовов context-chunks-mcp ↔ llm-ladder: ТЗ интеграции

Статус: ТЗ на исполнение. Цифры — замеры 2026-10-08 на проде; сам прокси дорабатывается
в `trained-assist/context-chunks-mcp` (его код здесь не трогается).

Компаньон: [spec-compression-threshold-for-context-chunks-mcp.md](./spec-compression-threshold-for-context-chunks-mcp.md) —
**когда** сжимать (350 КБ базовый, 100 КБ перед платной). Здесь — **как строится граф вызовов**
и какие ограничения лестницы он обязан учитывать.

---

## 1. Границы

Прокси сидит **перед** лестницей: `клиент → прокси → лестница`. Всё, что делает прокси
со входом, он делает **один раз** (принцип из ТЗ прокси: «сжатие только один раз на входе»).
Дальше — только вызовы лестницы.

Сжатие **не окончательное**: из него уходят **ref'ы** — указатели на куски оригинала, лежащие
в кэше прокси (`SHA-256`,100 записей, 30 мин, LRU). Модель читает сжатое представление и,
если нужна деталь, просит ref через MCP `get_context`.

Ожидаемое сжатие (цифра владельца): **~92 %** контекста. Замер на реальном запросе600 КБ →
~90 КБ (6.7×). Обе цифры должны подтвердиться на бенче.

## 2. Граф вызовов

```
клиент
  │  POST /v1/chat/completions, messages = P
  ▼
ПРОКСИ
  │
  ├─ sizeof(P) < порога ─────────────────────────────────────────────────┐
  │      (350 КБ;100 КБ если маршрут «перед платной»)                    │
  │                                                                      │
  │   ВЫЗОВ 1 — лестница, model = <лестница клиента>, messages = P       │
  │      → ответ клиенту  [ТЕРМИНАЛ]                                     │
  │                                                                      │
  └─ sizeof(P) ≥ порога → СЖАТЬ P → C (+ ref'ы в кэш)                   │
         │                                                               │
         ▼                                                               │
      ВЫЗОВ 1 — лестница, model = <лестница клиента>, messages = C       │
         │                                                               │
         ├─ ответил текстом → клиенту  [ТЕРМИНАЛ]                       │
         │                                                               │
         └─ ответ = «нужны ref'ы R1» (контракт §4)                      │
              │                                                          │
              ▼                                                          │
           ВЫЗОВ 2 — ПИН ladder_rung = opencode-go/mimo-v2.6-flash       │
                    messages = C + распакованные R1                      │
              │                                                          │
              ├─ ответил → клиенту  [ТЕРМИНАЛ]                          │
              └─ снова «нужны ref'ы R2»                                  │
                   │                                                     │
                   ▼                                                     │
                ВЫЗОВ 3 — ПИН тот же, messages = C + R1 + R2             │
                   ├─ ответил → клиенту  [ТЕРМИНАЛ]                     │
                   └─ иначе → вернуть лучший ответ/сжатый контекст      │
                                                                              │
      плюс опционально: если финальный ответ не JSON →                     │
      ВЫЗОВ N «переформатируй в JSON», ПИН тот же, вход = только ответ      │
      (маленький: объём данных там резко меньше)                            │
```

Число обращений к лестнице на один вход клиента — **жёстко ≤ 4**:
1 основной + 2 распаковки + 1 переформатирование. Это потолок, а не план.

## 3. Правила, из-за которых граф не превращается в петлю

### 3.1 Внутренние вызовы идут ТОЛЬКО на лестницу, никогда — на сам прокси

`LADDER_URL` для вызовов 2/3/N — это базовый адрес лестницы, а не адрес прокси. Если
внутренний вызов пойдёт через прокси, сжатие применится ко входу, который уже сжат, —
и получится петля без всякой пользы. Проверка на приёмке: во внутренних вызовах заголовка
прокси нет, и прокси логирует ровно один вход на клиентский запрос.

### 3.2 Второй/третий вызов — ТОЛЬКО пин, никакого обхода с головы

`ladder_rung: "opencode-go/mimo-v2.6-flash"`. Пин существует во **всех** не-фри лестницах
(проверено по `config/ladders.json`), то есть валиден при любом `model` клиента.

Почему это критично: при пине лестница кладёт модель первой, **но если она не влезает по
размеру, `fits()` её пропускает и обход продолжается по всем остальным ступеням**
(`src/ladder.js:712`: `outcome: 'skipped'` → `continue`). То есть «пин, который не влез»
молча превращается в полный обход с головы — ровно та кривая петля, которой надо избежать.

Поэтому ниже — жёсткое ограничение на размер внутреннего вызова.

### 3.3 Внутренний вызов обязан влезать в потолок Go

Потолок `opencode-go/*` = **100 000 токенов ≈ 400 000 байт** (`bytes/4`, `src/size-policy.js`).
Проверка в прокси **до** вызова:

| вход2 | что делает прокси |
|---|---|
| ≤ 350 000 байт | пин на mimo, как задумано |
| 350 000 … 900 000 байт | пиновать **big-window ранг**: `openrouter/nvidia/nemotron-3-ultra-550b-a55b:free` (окно 1 000 000) — он есть в каждой не-фри лестнице |
| > 900 000 байт | **не распаковывать**: вернуть лучший ответ/сжатый контекст + флаг `truncated_refs`. Распаковка куска на15K символов не стоит того, чтобы ронять вызов в полный обход |

### 3.4 Ограничение числа ref'ов за один вызов

Один ref = кусок до `MAX_CHUNK_SIZE` = 15 000 символов (~15–45 КБ байтами). Если модель
попросила10 ref'ов, вход2 = C + 150K символов — уже полпотолка. Правило: **за раз
распаковывать не более 3 ref'ов**, остальные отложить на следующий вызов (он и так заложен
в потолок из4 обращений).

### 3.5 Внутренние вызовы — не стрим, с малым max_tokens и таймаутом

`stream: false` (синтез потока и TTFB-логика тут ни к чему), `max_tokens` — по задаче
(переформат в JSON: ~2 000; распаковка: ~8 000), `ladder_timeout_ms` ≤ 30 000,
`ladder_total_timeout_ms` ≤ 60 000. Всё это уже клампится лестницей (`src/handler.js`).

## 4. Контракт «мне нужны ref'ы»

Основной вызов получает от модели не произвольный текст, а структурированный отказ.
Рекомендуемый формат (JSON в `content`):

```json
{ "answer": null, "need_refs": ["<ref1>", "<ref2>"], "question": "короткий вопрос модели к себе" }
```

- `answer: null` + непустой `need_refs` → прокси распаковывает и делает вызов 2;
- `answer: "…"` → терминал, ref'ы не нужны;
- не-JSON → вызов «переформатируй в JSON» (маленький вход).

Чтобы модель отдавала такой JSON, основной вызов должен идти с
`response_format: { type: "json_object" }` — лестница прокидывает его дальше, а на моделях,
которые отвечают на это 400, сама снимает и повторяет (`RF_400_RE`, `src/ladder.js`).

## 5. Что платит каждый вызов

| вызов | вход | кто отвечает (обычно) | стоимость |
|---|---|---|---|
| 1 (без сжатия) | P (до 350 КБ) | бесплатный Go (`longcat-2.5-preview-free`), бенч **39/39**, 7–11 с | бюджет Go $0 (free, unlimited limited-time) |
| 1 (сжатый) | C ≈ 8 % от P | то же, быстрее | то же |
| 2, 3 | C + ≤3×15K символов | **mimo-v2.6-flash** (пин) | месячная квота Go: **$0.14 / $0.28 за 1M** |
| N (JSON) | только ответ | mimo-v2.6-flash | копейки |

При сжатии92 % даже три обращения к mimo дешевле одного несжатого входа в платный ранг:
1M несжатых токенов = $0.28 против ~80K сжатых × 3 ≈ $0.007.

## 6. Атрибуция и наблюдаемость

Каждый вызов прокси обязан нести `x-ladder-app: context-chunks-mcp` (и `x-ladder-app-title`),
иначе в `/v1/analytics` вызовы прокси смешаются с трафиком агентов (#136).

Что логировать в прокси (нужно для бенча из companion-дока):

- размер входа и выхода каждого вызова (байты `JSON.stringify(messages)`);
- `rung`/`model`-победитель из ответа лестницы;
- число `get_context` и сколько ref'ов распаковано;
- итоговый терминал (какой вызов ответил) и причину, если дошли до потолка в §3.3.

## 7. Открытые вопросы (решать с владельцем до кода)

1. Что возвращать клиенту, если вызов2/3 не дали ответа: сжатый контекст как есть (модель
   продолжит без деталей) или явную ошибку `truncated_refs`?
2. Нужен ли вызов N (переформат в JSON) всегда, или только когда клиент явно ждёт JSON?
3. Кто кэширует ref'ы при рестарте прокси: ин-мемори (сейчас) или Redis/D1? При рестарте
   распаковка вернёт «ref не найден» — как тогда вести себя вызов2?
4. Порог «перед платной» (100 КБ) применяется только к входу клиента или и ко входу2?

## 8. Чеклист интеграции

1. Внутренние вызовы идут на `LADDER_URL`, не на адрес прокси (§3.1) — проверяется логом.
2. Вызов2/3/N — только пин `opencode-go/mimo-v2.6-flash`, иначе big-window ранг (§3.2–3.3).
3. Размер входа2 измеряется **до** вызова: `Buffer.byteLength(JSON.stringify(messages), 'utf8')`.
4. Потолок обращений — 4; при превышении возвращается лучший результат (§2).
5. `x-ladder-app: context-chunks-mcp` на всех вызовах (§6).
6. Прогон A/B/C/D бенча из companion-дока + отдельный замер: сколько `get_context` на вызов
   (цель 0–2) и доля вызовов, дошедших до вызова3.
