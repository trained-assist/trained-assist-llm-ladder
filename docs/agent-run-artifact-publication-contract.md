# ТЗ: надёжная публикация артефактов рана в репозиторий пользователя

Статус: требует решения владельца. Дата: 5 октября 2026.
Связанный рисеч: [opencode-gha-runner#4](https://github.com/vovalikessmoothy-png/opencode-gha-runner/issues/4).

## Замер, который всё обосновывает

16 запусков через живой шлюз 5 октября 2026, кольцо из трёх репозиториев.
Агент отработал 16/16, `exitReason=completed`. **Артефакты легли 1/16.**

Лог неуспешного рана (`run_5de2b920-9cbf-4004-bb5e-30959889676d`, GHA 37279473319):

```
[gha-runner] artifact push failed: could not create branch agent-run/run_5de2b920-…
[gha-runner] result reported: exitReason=completed artifacts=0
```

Единственный успешный запуск — тот, где round-robin кольца случайно выбрал ровно тот
репозиторий, который стоял в `repository.fullName` (`recruiting-me/runs` →
`recruiting-me/runs`, ветка `agent-run/run_a420f966-…`, `artifacts/report.md`, 20 байт).
Совпадение репозитория кольца с репозиторием задачи — единственное условие успеха,
и оно случайно.

## Причина

Джоба публикует выходы через Contents API в `spec.repository.fullName` токеном
`ARTIFACTS_TOKEN` — а это секрет самого репозитория кольца
(`opencode-gha-runner/ring/provision.sh:76` кладёт туда тот же токен, которым
провижнен сам репозиторий кольца).

Токен репозитория кольца по построению не может писать в чужой репозиторий. Это не
гонка, не отказ сервиса и не ра��овая ошибка прав: сбой детерминирован и ждёт каждого
прогона, цель которого отличается от места запуска.

## Что именно нужно решить

Ниже — три независимых вопроса. Первые два обязательны, третий следует из них.
Объединять их в один «компонент» нельзя: у каждого своя граница и свой владелец прав.

### 1. Откуда берётся токен публикации

Факт: легального канала токена в воркер сегодня нет. Наше API принимает
`repository.token` в `SubmitRequest` (`ai-agent-runner` `src/contracts/run-spec.ts:100-103`)
и **намеренно его не пересылает** в `LaunchRequest`
(`external-worker-adapter.ts:407`). Воркер берёт `ARTIFACTS_TOKEN` из кольца.

Варианты:

| | Механизм | Цена |
|---|---|---|
| A | Токен на `repository.fullName` от клиента, через claim-протокол | Клиентская кода должна уметь давать токен; для публичных репо он не нужен, для приватных — обязателен |
| B | Воркер публикует в репозиторий кольца, клиенту отдаётся ссылка | Артефакт лежит в чужом репозитории; ветка `agent-run/<runId>` теряет смысл как единица мержа |
| C | Артефакты отдельным объектом в GCS, ссылка в `LaunchResult.artifacts` | Артефакт не в git; нужен пожизненный доступ к бакету или подписанные ссылки |

Требование к любому варианту: **токен не должен попасть в `inputs` диспатча**.
`workflow_dispatch` публичного репозитория показывает inputs в метаданных прогона и
в логах — это уже сделано для `llmKey` через claim-протокол
(`opencode-gha-runner` `src/claim.ts:3-13`), и токен репозитория обязан идти тем же
путём: хранится в записи рана, выдаётся один раз по одноразовому `claimToken`,
гасится после первого claim'а.

### 2. Что делает рапорт, когда публикация невозможна

Факт: сегодня это `completed artifacts=0`. Клиент получает успешный ран без единого
выхода, и по коду отказа отличить это от «агент ничего не производил» нельзя.

Требование: публикация объявленных `outputs` — часть успеха, а не украшение. Ран с
объявленными выходами, которые не опубликованы, обязан быть отказом
(`failureClass: finalization`, отдельный код отказа), а не `completed`.
Отмена и таймаут здесь не при чём — это другой исход.

Пересекается с [opencode-gha-runner#1](https://github.com/vovalikessmoothy-png/opencode-gha-runner/issues/1):
там уже требуется, чтобы exit-0 агент с незавершённой публикацией давал явный
`finalization`-отказ. Здесь нужен **один ответ на оба случая** — иначе появятся два
кода отказа на одну причину.

### 3. Что кольцо значит для прав публикации

Кольцо решает задачу потолка параллельных джоб и egress-адреса, но не задачу прав.
Сегодня эти две вещи связаны одной сущностью — токеном репозитория кольца, который
одновременно и «впускает» запуск, и «выпускает» результат. Развязка обязательна:
иначе добавление репозитория в кольцо молча меняет права на публикацию для всех
остальных.

Минимальное требование: набор прав публикации не должен выводиться из факта
«репозиторий входит в кольцо». Если выбран вариант B или C, токен кольца публикацией
не занимается вообще, и вопрос снимается сам.

## Границы приёмки

- 8+ прогонов подряд, `repository.fullName` заведомо не совпадает ни с одним
  репозиторием кольца: `outcome=succeeded` **и** `outputRefs` непустой у каждого.
- Ни одного `completed artifacts=0` у рана с объявленными `outputs`.
- Токен публикации не виден ни в `inputs` прогона, ни в его логах.
- Отмена рана, у которого токен публикации не пришёл, даёт осмысленный отказ, а не
  падение на середине публикации.

## Чего это ТЗ не решает

- Синхронизацию курсора round-robin при параллельных запусках (5 параллельных прогонов
  ушли в один репозиторий кольца — кольцо не снижает потолок, а это отдельный дефект).
- Отмену, приходящую как `failed`: это
  [ai-agent-runner#133](https://github.com/trained-assist/ai-agent-runner/issues/133),
  дефект валидатора на стороне API, к публикации артефактов отношения не имеет.
