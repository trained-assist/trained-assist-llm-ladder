# Аналитика бенчмарков и план перехода на многокритериальный выбор моделей

Issue: #337. Статус: Фазы 0, 1, 3 и 4 (тесты) — готовы. Фаза 2 (подключение скоринга к лестнице) — отложена, ждёт, пока бенч отстоится в проде.

## Решение владельца (2026-10-29)

> Скорость — самое важное. Но модели с плохим качеством брать нельзя. Проверки на умение выдавать
> JSON и решать стандартные задачи — как минимум базовые. Контекстное окно, наверное, не ограничивает:
> берём всех проходящих по окну и ранжируем по минимальной латентности. **Разделять: сейчас мы
> делаем хороший крутой бенч, где будут все данные, а апдейты лестницы подстраиваем под него,
> когда бенч готов и протестирован.**

Следствие для архитектуры: качество — это **не вес в сумме, а жёсткий порог** (gate). Модель, провалившая
базовые задачи, не попадает в лестницу независимо от скорости. Скорость остаётся главным ранжирующим
сигналом; контекстное окно — фильтр («влезает/не влезает»), а не источник предпочтения. Составной
`score()` с весами **не строим** — строим бенч, который собирает все данные для будущего решения.

## 1. Что мерил бенч до #337 (исходное состояние)

Бенчмарки живут в `src/free-models.js` и пишутся в таблицу `free_model_benchmarks`
(миграция 0007). Один замер — это 3 тира по **байтам** промпта:

| Тир | Байты промпта | ≈ токены (`estimateTokens`, bytes/4) |
|---|---|---|
| small | 1 024 | ~280 |
| medium | 32 768 | ~9 000 |
| large | 131 072 | ~36 000 |

На каждый тир — **2 попытки**, записываются поля:

| Поле | Смысл | Кто использует |
|---|---|---|
| `p50_ms` | медиана времени ответа (скорость) | сортировка Go-блока, «полоса» OR-блока |
| `correct` | ответ содержит «ready» (regex `\bready\b`) | tie-break в OR-блоке |
| `successes/attempts` | доля отвеченных попыток | порог готовности (`≥2`) |
| `out_tokens` | сколько токенов потратил ответ | `benchInjectable` (не reasoning) |
| `truncated` | упёрся ли в `max_tokens=1500` | `benchInjectable` (не reasoning) |
| `last_error` | текст последней ошибки | диагностика |

Порог «модель готова»: `bench_status='ready'`, каталог `available`, `attempts≥2`, `successes≥2`, `p50_ms` конечен.

**Кого бенчмарчат:** только `opencode-go/*-free` и `openrouter/*:free`.
**Перебенч:** раз в 24 ч или если статус не `ready`. **Лимит:** 3 модели за прогон (`benchLimit=3`).
**Истории нет:** UPSERT по `(provider, model_id)` — хранится только последний замер.

## 2. Как выбор использует бенчи

`src/go-routing.js` переупорядочивает свободные блоки лестницы:

### Go free (`orderBenchmarkedGoRungs`)
Сортировка **только по `p50_ms`**. Качество (`correct`) не участвует вообще.
Контекст не участвует (для Go — эмпирический `GO_CONTEXT` из `size-policy.js`, только потолок).

### OpenRouter free (`orderOpenrouterRungs`)
1. Полоса по скорости: `fastest × 1.25 + 500 ms`.
2. Внутри полосы: `correct → context → p50` (качество — tie-break, контекст — tie-break).
3. Вне полосы: только `p50`.

### Контекст в `run()`
`canFitTokens()` — жёсткий потолок: модель с меньшим окном скипается ДО запроса.
Это фильтр, а не ранжирование: при равной скорости модель с окном 1M не выигрывает у 256K.

## 3. Данные качества, которые есть, но не используются

`config/model-quality.json` — внешние бенчмарки для 4 моделей:
- `big-pickle` — SWE Atlas 50.8%
- `space-bunny-free` — Terminal-Bench 2.1 52.1%
- `nemotron-3-ultra-free` — NVIDIA Code 85.3% / LiveCodeBench 86%
- `exo-free` — «unknown»

`grep` по `src/` и `scripts/` не находит ни одного использования — **данные мёртвые**.
Ключ — bare-имя модели (после последнего `/`), потому что одна модель живёт под несколькими
префиксами (`opencode-zen/big-pickle` ≡ `zen-rings/big-pickle`).

## 4. Что сделано в #337 (Фазы 1, 3, 4)

Бенч расширен, чтобы собрать ВСЕ данные для будущего решения, не трогая роутинг:

- **Стандартные задачи** (`BENCH_TASKS`, 2 попытки каждая): JSON-валидность (`{"answer":42,"ok":true}`), арифметика (`13×17=221`), короткий текст. Прогоняются по `sendOne` (общий для Go и OpenRouter), `check` оценивает собственный ответ модели.
- **`quality_summary`** (колонка в `free_model_benchmarks`, миграция 0019): `{correct_rate, json_valid, task_pass, quality (0..1), external, measured_at}`. `quality` — среднее из трёх сигналов, `null` если задачи не гонялись (`withTasks:false`).
- **`model-quality.json` подключён** (`loadModelQuality`, кеш 5 мин): ключ — bare-имя, идёт в `external` как provenance, **никогда не перекрывает замер**. В Worker без `node:fs` возвращает `{}`.
- **История замеров** (`free_model_bench_history`, 0019): временной ряд по тирам + строка `tasks` (`json_valid`, `task_pass`). Пишется в `collectFreeModels` когда `db` передан; prune через 180 дней.
- **Ротация ключей OR** вынесена в `sendOne`, реальный `http_429` сохраняется (не заменяется обобщённым `http_0`).
- **Отчёт** показывает `json ✓/✗ · tasks ✓/✗ · quality NN.NN` и раскладку задач.

Роутинг **не тронут**: `go-routing.js` сортирует по `p50_ms`, качество — только tie-break в OR-блоке, контекст — жёсткий потолок. Это осознанно: бенч должен отстояться в проде, прежде чем под него подстраивать лестницу.

**Тесты:** 7 новых (JSON-задачи, гейт, OR-shape, тайры-only, ротация ключей, склейка `external`). Всего 504 зелёные.

## 6. Целевая модель скоринга (Фаза 2 — будущее)

```
gate(model, tier) = context_ok && json_valid && task_pass   // жёсткий порог
score(model, tier) = normLatency(p50_ms)                    // скорость — главный ранжирующий сигнал
```

- `normLatency` — инверсия p50, нормированная по полосе кандидатов (0..1).
- `quality` — **gate**, не вес: провалившая базовые задачи не попадает в выбор.
- `external` (model-quality.json) — для моделей, которых мы ещё не замерили.
- Контекст — фильтр «влезает/не влезает», не источник предпочтения.

## 8. Открытый вопрос (владелец)

Когда бенч отстоится и появятся данные по реальным моделям — обсудить пороги гейта (`json_valid && task_pass`) и формулу `normLatency`. Веса `w_latency / w_context / w_quality` больше не нужны: качество = gate, скорость = ранжирование.
