# Аналитика бенчмарков и план перехода на многокритериальный выбор моделей

Issue: #337. Статус: Фаза 0 — зафиксировано текущее состояние и целевая модель.

## 1. Что бенчи меряют сегодня

Бенчмарки живут в `src/free-models.js` и пишутся в таблицу `free_model_benchmarks`
(миграция 0007). Один замер — это 3 тира по **байтам** промпта:

| Тир | Байты промпта | ≈ токены (`estimateTokens`, bytes/4) |
|---|---|---|
| small | 1 024 | ~280 |
| medium | 32 768 | ~9 000 |
| large | 131 072 | ~36 000 |

На каждый тир — **2 попытки**, записываются поля:

| Поле | Смысл | Кто использует |
|---|---|---|
| `p50_ms` | медиана времени ответа (скорость) | сортировка Go-блока, «полоса» OR-блока |
| `correct` | ответ содержит «ready» (regex `\bready\b`) | tie-break в OR-блоке |
| `successes/attempts` | доля отвеченных попыток | порог готовности (`≥2`) |
| `out_tokens` | сколько токенов потратил ответ | `benchInjectable` (не reasoning) |
| `truncated` | упёрся ли в `max_tokens=1500` | `benchInjectable` (не reasoning) |
| `last_error` | текст последней ошибки | диагностика |

Порог «модель готова»: `bench_status='ready'`, каталог `available`, `attempts≥2`, `successes≥2`, `p50_ms` конечен.

**Кого бенчмарчат:** только `opencode-go/*-free` и `openrouter/*:free`.
**Перебенч:** раз в 24 ч или если статус не `ready`. **Лимит:** 3 модели за прогон (`benchLimit=3`).
**Истории нет:** UPSERT по `(provider, model_id)` — хранится только последний замер.

## 2. Как выбор использует бенчи

`src/go-routing.js` переупорядочивает свободные блоки лестницы:

### Go free (`orderBenchmarkedGoRungs`)
Сортировка **только по `p50_ms`**. Качество (`correct`) не участвует вообще.
Контекст не участвует (для Go — эмпирический `GO_CONTEXT` из `size-policy.js`, только потолок).

### OpenRouter free (`orderOpenrouterRungs`)
1. Полоса по скорости: `fastest × 1.25 + 500 ms`.
2. Внутри полосы: `correct → context → p50` (качество — tie-break, контекст — tie-break).
3. Вне полосы: только `p50`.

### Контекст в `run()`
`canFitTokens()` — жёсткий потолок: модель с меньшим окном скипается ДО запроса.
Это фильтр, а не ранжирование: при равной скорости модель с окном 1M не выигрывает у 256K.

## 3. Данные качества, которые есть, но не используются

`config/model-quality.json` — внешние бенчмарки для 4 моделей:
- `big-pickle` — SWE Atlas 50.8%
- `space-bunny-free` — Terminal-Bench 2.1 52.1%
- `nemotron-3-ultra-free` — NVIDIA Code 85.3% / LiveCodeBench 86%
- `exo-free` — «unknown»

`grep` по `src/` и `scripts/` не находит ни одного использования — **данные мёртвые**.
Ключ — bare-имя модели (после последнего `/`), потому что одна модель живёт под несколькими
префиксами (`opencode-zen/big-pickle` ≡ `zen-rings/big-pickle`).

## 4. Чего не хватает (gap list)

| # | Пробел | Следствие |
|---|---|---|
| 1 | **Нет составного скоринга** (латентность + контекст + качество) | доминирует скорость |
| 2 | **Качество не участвует в Go-блоке** | быстрый, но слабый Go-ранг ведёт лестницу |
| 3 | **`model-quality.json` не подключён** | внешние данные качества не влияют на выбор |
| 4 | **Контекст не ранжирует** | не отдаём предпочтение большому окну |
| 5 | **`correct` — слабый прокси** (regex «ready») | нет содержательной оценки качества |
| 6 | **Тайры в байтах, роутинг в токенах** | рассогласование шкал |
| 7 | **Нет истории замеров** | не видно стабильности p50 |
| 8 | **`benchLimit=3`** | медленное покрытие каталога |
| 9 | **Веса не конфигурируются** | выбор не настраиваем, не обоснован данными |

## 5. Целевая модель скоринга

```
score(model, tier) =
    w_latency × normLatency(p50_ms)
  + w_context × normContext(context_window)
  + w_quality × quality(model)
```

- `normLatency` — инверсия p50, нормированная по полосе кандидатов (0..1).
- `normContext` — log-шкала окна (256K=0.5, 1M=1.0), для Go — `GO_CONTEXT`.
- `quality` — составной: `correct` (наш замер) + `model-quality.json` (внешний), по bare-имени.
- Применяется в ОБОИХ блоках (Go + OR), контекст перестаёт быть только потолком.
- Веса — конфигурируемы (env/конфиг), дефолты обоснованы владельцем (см. issue #337).
