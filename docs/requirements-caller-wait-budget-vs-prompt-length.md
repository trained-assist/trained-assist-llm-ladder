# Требования к бюджету ожидания вызывающего и его зависимости от длины промпта

Статус: **проект требований**, на согласование. Написан 2026-10-08 по замерам этой сессии.

Зачем отдельно: выяснилось, что система **систематически не доставляет ответ вызывающему** —
69 % успешных ответов зена приходят уже после того, как вызывающий ушёл. Это не свойство
провайдера, а **нарушение требования**, и пока требование не записано, «починить» нечего:
можно лишь спорить, быстрее оно или медленнее.

---

**Смежный документ:** [требования к гонке зена по вероятности успеха](./requirements-hedge-by-success-probability.md) —
план владельца «пара → две пары → три пары», пересчитанный на те же замеры. Этот файл про то,
**дожидается ли** вызывающий; тот — про то, **сколько раз** просить провайдера, чтобы дождался.

---

## 1. Измеренные зависимости (не гипотезы)

### 1.1 Время растёт с длиной промпта

`provider_ms` у **успешных** задач зена, среднее по размеру входа:

| вход | zen |
|---|---|
| `<5 KB` | **9.4 с** |
| `5–20 KB` | **42 с** |
| `20–50 KB` | **45 с** |

Бесплатный Go (замеры на живом проде, пин на `opencode-go/longcat-2.5-preview-free`):

| вход | время |
|---|---|
| ~60 токенов | 5.2–6.6 с |
| ~1.5K токенов | 6.0–8.6 с (один зов — 8.3 с на границе потолка) |
| ~18K токенов (74 КБ) | 3.9 с |
| ~49K токенов (363 КБ) | 13.5 с |

OpenRouter `:free` при **138K токенов (1.03 МБ)**: **12.3 с** — длинные промпты обслуживает
именно он, потому что потолок Go (100K) и байтовый гард зена (50 КБ) отсекают свои ранги
**до** попытки.

### 1.2 Полное время задачи зена (2911 успешных)

| этап | p50 | p90 |
|---|---|---|
| очередь `enqueued → claimed` | **15.8 с** | 3011 с\* |
| сервис воркера `claimed → finished` | **24.8 с** | 58.7 с |
| **итого** | **56.3 с** | 3043 с\* |

\* p90 и max отравлены окном простоя кольца (задачи висели часами) — опорная величина **p50**.

### 1.3 Бюджет вызывающего

`wait_ms` = `ladder_timeout_ms` (дефолт **20 000**) → `MAX_WAIT_MS` 90 000 → при `504`
дополнительная `graceMs` **15 000** (`ringCall`). Итого вызывающий ждёт зена **не более 35 с**.

| | |
|---|---|
| укладывается в 35 с | **889 из 2911 (31 %)** |
| не укладывается | **2022 из 2911 (69 %)** |
| только zen, без учёта очереди | 1893 из 2911 (65 %) |

### 1.4 Почему падения дешёвые (чтобы не путать с ожиданием)

Провалы приходят **быстро**, а не по таймауту: `provider_ms` p50 = 0.67 с (`<20K`),
0.83 с (`20–50K`), 6.6 с (`≥50K`), и **90–94 % из них — пустой ответ**. Ожидать здесь нечего:
успешные идут 18–42 с, то есть медианный провал — это «zen ничего не вернул», а не
«браузер не дождался».

## 2. Требования

Формат: **R-номер · формулировка · измеримый порог · как проверить**.

### R1 · Ответ доходит до вызывающего

Если провайдер вычислил ответ, вызывающий обязан его получить.

> **Порог:** ≥ 90 % задач в `state='done'` укладываются в бюджет вызывающего (`wait_ms` +
> `graceMs`), измеряется как `finished_at − enqueued_at ≤ wait_ms + grace_ms`.
>
> **Было 41.4 %** на здоровом окне (бюджет 35 с). После варианта Б (§3) бюджет кольца поднят до
> 60 с → расчётная доставка **74.8 %**. **Требование всё ещё НЕ выполняется** — до 90 % не хватает
> ~15 п.п., дальше цена уже не ожидание, а сама медленность zen (сервис p90 63 с).

### R2 · Бюджет ожидания — функция длины промпта, а не одно число

Одно число (20 с) не может покрыть и 9 с на `<5 KB`, и 45 с на `20–50 KB`. Бюджет назначается
по полосе входа; полосы зафиксированы в `src/size-policy.js` (`BANDS`) и должны использоваться
и при назначении `wait_ms`, а не только при решении «гонить или нет».

> **Порог:** `wait_ms` монотонно не убывает с полосой; для каждой полосы задан целевой верх.
>
> **Сейчас:** полосы влияют только на число параллельных попыток и на множитель бюджета
> **бесплатного Go** (`isFreeGo ? … : rungBudget`), бюджет зена один для всех полос.

### R3 · Очередь — часть времени ответа, но не часть времени провайдера

Очередь съедает бюджет до того, как zen вообще начал. Вызывающий платит за неё, провайдер —
нет; значит и ограничивать её надо отдельно.

> **Вариант А (считать от выдачи):** бюджет отсчитывается от `claimed_at`, а не от `enqueued_at`.
>
> **Вариант Б (урезать очередь):** p90 `claimed_at − enqueued_at` ≤ 5 с.
>
> **Статус: на здоровом окне (с 2026-10-07 09:00) очередь p50 = 0 с — А и Б сейчас почти не дают.**
> Но в окно 10-05 13:00 → 10-06 02:00 **54–100 %** задач ждали больше 5 минут (p75 = 8.4 мин,
> max > 4 часов), когда кольцо было сломано. То есть ограничение очереди — страховка на случай
> возврата того состояния, а не способ поднять доставку сегодня. А, как показал замер (§3), на
> здоровом окне даёт лишь 52.7 % против 74.8 % у простого поднятия бюджета.

### R4 · Отказ быстрее ожидания

Если вероятность ответа в отведённом бюджете ниже порога — отказывать локально, не создавая
задачи, не тратя квоту и не занимая воркера.

> **Порог:** отказ за ≤ 1 с, при этом `zen_pool_tasks` не пополняется и `zen_budget` не растёт.
>
> **Сейчас: выполняется** — `ZEN_MAX_INPUT_BYTES` (50 КБ) и модельный
> `ZEN_MODEL_MAX_INPUT_BYTES` (`mimo-v2.6-flash-free` → 20 КБ) отвечают 413 за 0.4–0.6 с.

### R5 · Потолок входа — на модель, а не на всё подряд

> **Порог:** у каждой модели с достаточным объёмом наблюдений свой потолок; отказ называет своё
> число (`limit=…`), а не общее.
>
> **Сейчас: выполняется** для `mimo-v2.6-flash-free` (20 000 против общих 50 000).

### R6 · Потолок ранга по размеру — до попытки

Ранг, чьё окно меньше входа, не должен вызываться вообще: его отказ стоит дороже отказа.

> **Порог:** при входе выше потолка в `attempts` — `outcome: 'skipped'`, вызовов провайдеру нет.
>
> **Сейчас: выполняется** — `opencode-go/*` 100 000 токенов; замер: вход ~130K токенов даёт
> `skipped: input ~130008t above the rung ceiling` за **0.43 с** вместо прежних 48 с и трёх
> сожжённых ключей.

### R7 · Нижняя граница: не убивать здоровую модель ради скорости

Быстрый бюджет имеет смысл только если модель успевает ответить здоровой.

> **Порог:** множитель бюджета ≥ p95 времени ответа быстрого ранга в этой полосе.
>
> **Сейчас: после правки — выполняется** (0.6 → 12 с при p95 ≈ 10 с; до правки 0.4 → 8 с
> резал здоровые ответы 8.0–8.6 с — одна попытка из пяти).

## 3. Что решилось и чем: Б, а не А

### Сначала — ошибка в исходной постановке

Первые цифры документа (p50 полного времени 56.3 с, доставка 31 %) **отравлены окном
10-05 13:00 → 10-06 02:00**, когда кольцо было сломано: тогда 54–100 % задач ждали в очереди
больше 5 минут (p75 очереди — 8.4 мин). На здоровом окне **с 2026-10-07 09:00** (1599 задач)
очередь почти исчезла:

| | здоровое окно | всё время |
|---|---|---|
| очередь p50 | **0 с** (p90 39 с) | 15 с (p90 3027 с) |
| сервис zen p50 | **33 с** (p90 63 с) | 24.8 с |
| итого p50 | **41 с** (p90 83 с) | 56.3 с |

Вывод: **очередь перестала быть проблемой** (см. гистограмму ниже в §1), а проблема осталась
одна — **бюджет 35 с меньше, чем сама модель** (сервис p50 33 с, p90 63 с).

### Сравнение вариантов на здоровом окне

| правило | доставлено | доля |
|---|---|---|
| **сейчас: 35 с от постановки** | 662/1599 | **41.4 %** |
| **А**: 35 с сервиса от `claimed_at` | 842/1599 | 52.7 % |
| А + стена 60 с | 772/1599 | 48.3 % |
| **Б: бюджет 60 с** | 1196/1599 | **74.8 %** |
| **Б: бюджет 90 с** | 1477/1599 | 92.4 % |

**Побеждает Б.** Очередь тут ни при чём (p50 = 0 с) — лечить надо бюджет.

### Что сделано (вариант Б, scoped только на кольцо)

`RING_WAIT_MS = 45_000` + `ringWaitMs(timeoutMs)` в `attemptRing` (`src/ladder.js`): пол в
`wait_ms`, который **только поднимает** — вызывающий, попросивший больше, больше и получит.

- 45 с `wait_ms` + 15 с `graceMs` = **60 с → 74.8 % доставки** (было 41.4 %);
- пол не превышает `MAX_WAIT_MS` пула (90 с), то есть edge-таймаут не задет;
- холодный или мёртвый кольцо сюда не попадает — эти ветки возвращаются **до** постановки
  задачи, поэтому 45 с не превращает отказ в ожидание;
- 60 → 90 с даёт ещё +18 п.п., но это уже 1.5 минуты ожидания — а «опенкод зависает» было
  главной жалобой, поэтому остановились на 60 с.

### Вариант В (очередь) остаётся отдельной задачей

На здоровом окне очередь почти нулевая, но в окно 10-05/10-06 она вырастала до часов —
это значит, что при остановке воркеров задачи копятся, и стена (предел `MAX_WAIT_MS`)
тогда всё равно их режет. Ограничение очереди (p90 ≤ 5 с) — страховка на случай возврата
того состояния, а не способ поднять доставку сегодня.

### Г

Зен как страховка, основа на быстром Go (#169) — остаётся рабочим допущением: пол бюджета
касается только пути, когда Go уже отказал.

## 4. Как проверять (приёмка)

Все пороги выше — из запросов к `trained-assist-llm-ladder-trace`. Базовые:

```sql
-- R1: доля доставки
SELECT COUNT(*) AS n,
       SUM(CASE WHEN finished_at - enqueued_at <= 35000 THEN 1 ELSE 0 END) AS in_budget
FROM zen_pool_tasks WHERE state = 'done' AND finished_at > 0 AND enqueued_at > 0;

-- R3: очередь отдельно от провайдера
SELECT CAST(AVG(claimed_at - enqueued_at) AS INT) AS queue_ms
FROM zen_pool_tasks WHERE claimed_at IS NOT NULL AND state = 'done';

-- 1.1: зависимость от размера
SELECT CAST(AVG(provider_ms) AS INT) AS zen_ms
FROM zen_pool_tasks WHERE state = 'done' AND length(messages) < 5000;
```

Мини-стенд для живой проверки полос — `npm run gate` плюс пин через
`ladder_rung` с нужным размером входа (см. `scripts/live-gate.mjs`).

## 5. Что уже сделано и что осталось

**Сделано:**
- **R4, R5, R6, R7** — выполнены (PR #169, #172, #173).
- **R1, шаг 1 (вариант Б)** — `RING_WAIT_MS = 45_000` и `ringWaitMs()` в `src/ladder.js`:
  бюджет кольца 20 → **45 с** (+15 с grace = **60 с**) → расчётная доставка **41.4 % → 74.8 %**.
  Пол только поднимает: вызывающий, попросивший больше, больше и получит.
- **Полосы** уже объявлены (`BANDS` в `src/size-policy.js`) и покрыты тестами — R2 требует
  только **применить** их к `wait_ms`, а не изобретать заново.

**Осталось:**
- **R1 до конца (90 %)** — с 60 с доставка 74.8 %; дальше прирост идёт ценой ожидания
  (90 с → 92.4 %), а не технологии. Дальше 60 с имеет смысл идти только с вариантом В
  (урезать очередь), иначе мы просто ждём дольше.
- **R2** — полосы применяются к числу попыток и к бюджету бесплатного Go, но `wait_ms` кольца
  остаётся одним числом: на `<5 KB` zen и так отвечает за 9.4 с, а бюджет у него 60 с.
- **R3** — очередь ограничена только стеной `MAX_WAIT_MS`. Страховки на случай остановки
  воркеров (окно 10-05/10-06, p75 очереди 8.4 мин) нет.

**Гонка** (PR #171) к этим требованиям отношения не имеет: она меняет шанс ответа, а не
гарантию доставки. План «пара → две пары → три пары» для зена — в соседнем документе.
