# Анализ структуры настоящих жирных промптов

Замер 2026-10-08. Ответ на вопрос «какие промпты реально приходят и из чего они состоят» —
потому что `'x'.repeat(N)` и реальный промпт разные вещи, а все потолки и таймауты мы
калибровали именно на реальных.

Инструмент для воспроизведения: `scripts/make-fat-prompt.mjs` (собирает такой промпт из
настоящих данных и умеет отправить его в лестницу).

---

## 1. Два источника

| источник | что это | объём |
|---|---|---|
| `zen_pool_tasks.messages` (D1) | то, что **реально ушло** в лестницу | 5844 задачи |
| `~/.local/share/opencode/opencode.db` | чат **до** сборки: что вообще лежит в сессии | 281 419 частей, 66 602 сообщения, 847 сессий |

Первый источник — главный: он показывает не переписку, а **запрос**, каким его видит лестница.

---

## 2. Распределение по размеру и успех (все 5844 payload-а)

| размер | всего | доля | успешно | **успех** |
|---|---|---|---|---|
| `<5 КБ` | 1942 | 33.2 % | 1002 | **51.6 %** |
| `5–20 КБ` | 1994 | 34.1 % | 1242 | **62.3 %** |
| `20–50 КБ` | 1315 | 22.5 % | 732 | **55.7 %** |
| `50–200 КБ` | 33 | 0.6 % | 5 | **15.2 %** |
| `200 КБ–1 МБ` | 406 | 6.9 % | 66 | **16.3 %** |
| `≥1 МБ` | 153 | 2.6 % | 29 | **19.0 %** |

Два вывода, которые стоят отдельного внимания:

1. **90 % запросов меньше 50 КБ** (33.2 + 34.1 + 22.5). Порог `ZEN_MAX_INPUT_BYTES = 50 000`
   задевает ~12 % (692 задачи), а не «всё подряд» — то есть защита узкая и точная.
2. **Успех НЕ монотонно растёт с маленьким размером.** `<5 КБ` даёт 51.6 %, а `5–20 КБ` — 62.3 %.
   Жирность не вредит до 50 КБ, а **катастрофа начинается строго за порогом**: 55.7 % → 15–19 %.
   Это и есть эмпирическое обоснование потолка.

---

## 3. Жирность бывает двух разных видов

Из шести примеров (§4) явно выделяются две структуры:

**А. Один огромный вывод инструмента** — payload из **2–3 сообщений**, где одно занимает
49–169 КБ. Это `grep`/`read`, чей результат целиком лёз в контекст. Такие встречаются вплоть
до `200 КБ` и при этом почти не содержат истории.

**Б. Накопленная история** — payload из **58 … 1351 сообщений**, где половину составляют
выводы инструментов. Это живая сессия агента: он что-то читал, правил, читал снова.

Разбор 60 самых крупных payload-ов (1.07–2.0 МБ):

| роль | сообщений | доля |
|---|---|---|
| `tool` | 19 683 | 50.6 % |
| `assistant` | 18 859 | 48.5 % |
| `user` | 977 | 2.5 % |
| `system` | 46 | 0.1 % |

**Половина объёма — это выводы инструментов, а не текст пользователя.** Среднее число
сообщений — **860**, крупнейшее отдельное сообщение — **241 КБ**.

## 4. Шесть примеров (реальные payload-ы)

| корзина | байт | сообщений | user/assistant/tool/system | крупнейшее | что это |
|---|---|---|---|---|---|
| `<5 КБ` | 3 484 | 3 | 2 / 0 / 0 / 1 | 3 КБ | вызов инструмента (`tool_calls`) |
| `5–20 КБ` | 14 484 | 2 | 1 / 0 / 0 / 1 | **49 КБ** | вывод инструмента |
| `20–50 КБ` | 35 721 | 3 | 2 / 0 / 0 / 1 | **86 КБ** | вызов инструмента (`tool_calls`) |
| `50–200 КБ` | 122 349 | 2 | 1 / 0 / 0 / 1 | **169 КБ** | вывод инструмента |
| `200 КБ–1 МБ` | 362 633 | 58 | 1 / 28 / 28 / 1 | 81 КБ | вывод инструмента |
| `≥1 МБ` | ~2 000 000 | ~860 | 1 / 18 859 / 19 683 / 46 | **241 КБ** | вывод инструмента |

Первые пять разобраны целиком, шестой — по агрегату 60 самых крупных: его JSON больше 2 МБ
и не проходит через `wrangler d1 execute` одним куском.

Видно **перелом структуры**: до `200 КБ` это 2–3 сообщения с одним крупным вложением,
а дальше — десятки и сотни сообщений накопленной истории.

---

## 5. Что лежит в чате ДО сборки (`opencode.db`)

Состав частей сессии (281 419 штук):

| тип | штук | что это |
|---|---|---|
| `tool` | 76 465 | выводы инструментов |
| `step-start` / `step-finish` | 62 635 / 62 449 | границы шагов агента |
| `reasoning` | 51 138 | цепочки рассуждений |
| `text` | 20 170 | текстовые реплики, макс **83 532** симв. |
| `patch` | 8 547 | правки, крупнейшие ~937 КБ |
| `file` / `compaction` | 27 / 3 | — |

Крупнейшее **текстовое** содержимое инструмента — **188 878 символов** (вывод `grep`,
2026-09-22) ≈ 47K токенов **одним куском**.

Абсолютные рекорды по размеру — **картинки**: `state.attachments[0].url` это `data:image/png;base64,…`
длиной до **2 167 474 симв.** (2.17 МБ). То есть в чате есть части, которые крупнее любого
текста на порядок — но они идут отдельным attachment'ом, а не текстом в `messages`.

**Отсюда:** один фрагмент чата не даёт 300K токенов. Триста тысяч набираются только
**сборкой истории** — ровно так, как показывает §3 (860 сообщений, 19 683 из них tool).

---

## 6. Как структура ложится на защиты лестницы

| защита | задевает | что происходит |
|---|---|---|
| `ZEN_MAX_INPUT_BYTES` = 50 КБ | ~12 % payload-ов | 413 за 0.4 с, без задачи и без квоты; успех там 15–19 % против 55–62 % |
| потолок `opencode-go/*` = 100K токенов ≈ 400 КБ | входы `>400 КБ` | мгновенный `skipped` в `attempts`; раньше это стоило **48 с и трёх ключей** |
| `messages.slice(0, 2_000_000)` | **2 задачи из 5844** | обрезка делает JSON невалидным, но до zen не доходит — гард выше по коду срабатывает раньше (2 МБ ≫ 50 КБ) |
| таймаут | растёт с размером | zen: 9.4 с на `<5 КБ` → 42–45 с на `5–50 КБ` |

## 6а. Живая проверка: реальный промпт в 300K токенов

Собран `scripts/make-fat-prompt.mjs --tokens 300000` из реальных частей `opencode.db`
(32 сообщения, 1 285 232 байта, 400 настоящих кусков) и отправлен в лестницу без пина:

```
источник   : opencode.db (реальные части сессий)
сообщений  : 32      байт: 1 285 232      токенов: ~300007
ОТВЕТИЛ: openrouter/nvidia/nemotron-3-ultra-550b-a55b:free за 27.1 с, готово
```

Что показал проход по всем 14 рангам:

| ранг | что произошло |
|---|---|
| `opencode-go/longcat-2.5-preview-free` | `skipped: input ~314328t above the rung ceiling` — потолок 100K сработал |
| `opencode-go/mimo-v2.6-flash` | то же самое |
| 4 × `zen-rings/*` | `input is too long: 1283317 bytes, limit 50000` (mimo — `limit 20000`) |
| OR `:free` с контекстом 256–262K | не влезают в 300K → уходят дальше |
| **`nemotron-3-ultra-550b-a55b:free` (контекст 1M)** | **отвечает за 27.1 с** |

Из инвентаря: у бесплатных OpenRouter-рангов контексты **256 000 / 262 144 / 512 000 / 1 000 000** —
триста тысяч токенов физически помещаются только в `dots-studio/dots-3-note-preview:free` (512K)
и `nemotron-3-ultra-550b-a55b:free` (1M).

**Побочно прогон поймал баг самого генератора**: `role: 'tool'` без `tool_call_id` даёт
`HTTP 400 «tool messages must include a non-empty string tool_call_id»` — и ВСЕ шесть
бесплатных OR-рангов отказали на этом, а не на размере. Исправлено (assistant с `tool_calls`
→ tool со ссылкой на `call_…`).

---

## 7. Выводы

1. **«Жирный» ≠ «много текста».** Половина объёма самых крупных запросов — выводы
   инструментов (`tool`), и только 2.5 % — реплики пользователя.
2. **Два разных вида жирности** требуют разных ответов: один огромный вывод (лечится
   потолком размера) и накопленная история (лечится компакцией/окном, а не потолком —
   860 сообщений при каждом по отдельности вполне вменяемы).
3. **Порог 50 КБ подтверждён данными**: успех 55.7 % сразу за ним падает до 15–19 %,
   и задевает он при этом лишь ~12 % трафика.
4. **Триста тысяч токенов — это история, а не один промпт**: измеримо это
   ~860 сообщений / ~1 МБ+ JSON. Генератор `scripts/make-fat-prompt.mjs` собирает именно
   такую структуру, а не `repeat()`.
