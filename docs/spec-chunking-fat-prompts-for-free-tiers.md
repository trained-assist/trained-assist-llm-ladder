# ТЗ: чанкирование и предобработка жирных промптов (для соседней сессии)

Статус: ТЗ на исполнение. Все пороги — замеры 2026-10-08 на живом проде, не теория.

Кому: сессии, которая делает **чанкирование и предобработку** жирных запросов, чтобы они
**гарантированно попадали в бесплатные и быстрые лимиты**.

## 1. Лимиты, под которые надо попадать

**Важно: единицы у лимитов РАЗНЫЕ.** Ошибиться в них — получить отказ, который выглядит
как поломка модели.

| ранг | лимит | **в чём именно** | где в коде |
|---|---|---|---|
| `zen-rings/*` (общий) | **50 000** | **байт UTF-8** JSON `messages` | `ZEN_MAX_INPUT_BYTES`, `src/zen-ring.js` |
| `zen-rings/mimo-v2.6-flash-free` | **20 000** | байт UTF-8 | `ZEN_MODEL_MAX_INPUT_BYTES` |
| `opencode-go/*` | **100 000** | **токенов** (оценка `len/4`) | `INPUT_CEILING_TOKENS`, `src/size-policy.js` |
| `opencode-go/*` — фактический потолок шлюза | **~400 КБ тела** | байты | замер: 392 КБ ок → 491 КБ отказ |
| `openrouter/*:free` | 256 000 / 262 144 / 512 000 / 1 000 000 | токенов (per model) | инвентарь `free_models.context` |
| обрезка в кольце | 2 000 000 | байт | `messages.slice(0, 2_000_000)` |

### Почему единицы путаются

Байты UTF-8 для русского текста ≈ **1.8 × символы** (2 байта на кириллицу). Замер:

```
payload: 49 300 байт  ≈ 26 800 символов  ≈ 6 700 токенов (оценка len/4)
```

То есть **50 000 байт на русском — это ~27 000 символов, а не 50 000**. Ошибётесь в сторону
символов — получите `input is too long` на видимом «небольшом» промпте. Ошибётесь в сторону
токенов для Go — упрётесь в байтовый потолок шлюза, который код не проверяет.

### Замеренный практический водораздел

| путь | сработало | отказало |
|---|---|---|
| зен | **49 300 байт** → ответил | **116 300 байт** → `413 … 116289 bytes, limit 50000` за 0.6 с |
| бесплатный Go | **271 КБ / 61K токенов** → ответил (39/39 в бенче) | **523 КБ** → `429 Upstream request failed` |
| бесплатный Go, заведомо за потолком | — | **1 509 КБ / ~231K токенов** → `skipped: input ~231592t above the rung ceiling` за 0.6 с |

**Итоговые цели для чанкера:**

```
для зена      : messages (UTF-8) ≤ 45 000 байт      # запас под 50 000
для mimo в зене:               ≤ 18 000 байт        # запас под 20 000
для бесплатного Go:            ≤ 380 000 байт       # запас под ~400 КБ шлюза
для OR :free:                  ≤ 0.9 × context модели (из free_models)
```

## 2. Правила чанкирования

1. **Считать байты UTF-8, а не символы и не «примерные токены».** Единственный способ
   получить отказ — не угадать именно байты: `JSON.stringify(messages).length` в байтах
   (не `String.length`).
2. **Чанковать по границам сообщений**, никогда внутри:
   - не рвать `role`/`content`;
   - при наличии `tool_calls` — **обязательно** держать `assistant` с `tool_calls` и его
     парный `role: 'tool'` с тем же `tool_call_id` в одном чанке. Разнесёте — шлюз ответит
     `400 tool messages must include a non-empty string tool_call_id` (поймано на живом прогоне);
   - `system` дублировать в каждый чанк (иначе второй кусок отвечает без правил).
3. **Сохранять хвост, резать голову**: в каждый чанк кладём `system` + **последние** K сообщений;
   старое — сжатие (`summary`, `compaction`) либо отбрасывание. Свежий контекст решает задачу,
   старый — только съедает лимит.
4. **Считать до отправки, а не после отказа**: вызвать `estimateTokens` (сейчас `len/4`, в
   `src/size-policy.js`) и сравнить с потолком целевого ранга. Отказ по размеру — это 0.4–0.6 с
   (дёшево), но это **потерянный хоп**, а если дошли до шлюза Go — 429 с ротацией ключей.
5. **Не гнаться за 300K токенов в одном запросе.** Реальные жирные сессии рекрутинга —
   до 61K токенов (271 КБ) и обслуживаются бесплатным Go за 7–11 с (бенч: 39/39). Триста
   тысяч в одном запросе не нужны — нужны запросы, которые **влезают**.

## 3. Примеры запросов — с реальными результатами

Все пять прогнаны на проде сегодня. `pinn` = `ladder_rung` (пин, без фейловера), поэтому
видно поведение **конкретного** ранга.

### Пример A — маленький, быстрый (для зена и для всего остального)

```json
{
  "model": "service",
  "messages": [
    {"role": "system", "content": "Ты — ассистент по разбору кода."},
    {"role": "user", "content": "Напиши слово: ок"}
  ],
  "max_tokens": 30, "ladder_rung": "zen-rings/nemotron-3-ultra-free"
}
```

| размер | результат |
|---|---|
| **154 байт** | ✅ **ответил** |

### Пример B — предел зена (вписываемся в 50 000 байт)

```json
{ "model": "service",
  "messages": [
    {"role": "system", "content": "Ты — ассистент по разбору кода. Отвечай по фактам из предоставленного контекста."},
    {"role": "user", "content": "<300 повторов осмысленного текста, всего ~26 800 символов>"},
    {"role": "user", "content": "Ответь одним словом: готово"}
  ],
  "max_tokens": 30, "ladder_timeout_ms": 90000,
  "ladder_rung": "zen-rings/nemotron-3-ultra-free" }
```

| размер | результат |
|---|---|
| **49 300 байт** (≈6 700 токенов) | ✅ ответил, **но за 56.3 с** |

**Вывод:** в лимит влезает — но это НЕ быстро. Зен на верхней границе своих 50 КБ отвечает
порядка 50 с. Если нужен именно быстрый путь, цель — `<5 КБ` (там замерено 9.4 с), а не «всё
что влезает».

### Пример C — за пределом зена, но в пределах бесплатного Go

```json
{ "model": "service",
  "messages": [ … 116 289 байт UTF-8 … ],
  "max_tokens": 30, "ladder_timeout_ms": 90000,
  "ladder_rung": "zen-rings/nemotron-3-ultra-free" }
```

| размер | результат |
|---|---|
| **116 300 байт** | ❌ `input is too long for the free tier: 116289 bytes, limit 50000` за **0.6 с** |

**Отказ дешёвый и корректный** — 0.6 с, без задачи, без квоты, без воркера. Это и есть
правильное поведение: такой запрос **не должен** идти в зен. Его место — в бесплатном Go
(см. пример D), если он туда влезает.

### Пример D — большой, но в пределах бесплатного Go

```json
{ "model": "service",
  "messages": [ … 271 КБ / ~61 000 токенов (реальная сессия mbk_luda_recruiter) … ],
  "max_tokens": 64, "ladder_timeout_ms": 120000,
  "ladder_rung": "opencode-go/longcat-2.5-preview-free" }
```

| размер | результат |
|---|---|
| **271 КБ / ~61K токенов** | ✅ **ответил** |

Это не теория: на этом гонялся весь бенч жирных рекрутинговых сессий — **39/39 = 100 %**,
медиана **7–11 с** (`scripts/fat-session-bench.mjs --run`).

### Пример E — за потолком бесплатного Go

```json
{ "model": "service",
  "messages": [ … 1 509 343 байта ≈ 231 000 токенов … ],
  "max_tokens": 30, "ladder_timeout_ms": 90000,
  "ladder_rung": "opencode-go/longcat-2.5-preview-free" }
```

| размер | результат |
|---|---|
| **1 509 343 байта / ~231K токенов** | ❌ `input ~231592t above the rung ceiling` за **0.6 с** |

Тут работает размерный потолок (PR #169) — раньше это стоило бы **48 с и трёх сожжённых
ключей** (ротация на `429 Upstream request failed: Endpoint is unavailable`).

### Пример F — отдельный потолок mimo внутри зена (20 000 байт)

У `zen-rings/mimo-v2.6-flash-free` лимит **свой**, а не общий: 20 000 байт, а не 50 000.
Пин на него с промптом «на 25 КБ», фактически 63 917 байт:

```json
{ "model": "service",
  "messages": [ {"role":"system","content":"…"}, {"role":"user","content":"<63 917 байт>"} ],
  "max_tokens": 40, "ladder_timeout_ms": 90000,
  "ladder_rung": "zen-rings/mimo-v2.6-flash-free" }
```

| размер | результат |
|---|---|
| **63 910 байт** | ❌ `input is too long for the free tier: 63910 bytes, limit 20000` за **0.6 с** |

Правило: если целевой ранг — mimo, бюджет **18 000 байт**, а не 45 000. Общая таблица лимитов
(§1) даёт оба числа, но сравнить надо именно с лимитом той модели, на которую идёте.

### Пример G — OpenRouter `:free` с большим контекстом (вписалось)

`openrouter/nvidia/nemotron-3-ultra-550b-a55b:free` — контекст **1 000 000 токенов**
(контексты всех `:free` лежат в `config/prices.json` / инвентаре `free_models.context`):

```json
{ "model": "service",
  "messages": [ … 390 217 байт … ],
  "max_tokens": 40, "ladder_timeout_ms": 120000,
  "ladder_rung": "openrouter/nvidia/nemotron-3-ultra-550b-a55b:free" }
```

| размер | результат |
|---|---|
| **390 217 байт** | ✅ ответил за **24.8 с** |

Вывод: если промпт жирнее потолка Go (~400 КБ) — его место **не** в Go, а на `:free`-ранге с
нужным окном. Чанковать при этом всё равно нужно: 25 с — это не 7 с.

### Пример H — за контекстом самой модели OpenRouter

Тот же сеанс промптов, но 6 760 217 байт ≈ 1 693 039 токенов, пин на ранг с окном 262 144:

```json
{ "model": "service",
  "messages": [ … 6 760 217 байт ≈ 1 693 039 токенов … ],
  "max_tokens": 40, "ladder_timeout_ms": 90000,
  "ladder_rung": "openrouter/inclusionai/ling-3.0-flash-sante:free" }
```

| размер | результат |
|---|---|
| **6 760 217 байт / ~1 693 039 токенов** | ❌ `HTTP 400: maximum context length is 262144 tokens. However, you requested about 1693039 tokens` за **1.3 с** |

Это **не** переполнение лестницы и не переполнение потолка: лестница пропустила запрос, а
отказал сама модель. Отказ `context`-класса — `recordFailure` пишет `skipUntil = 0`, то есть
ранг **не** уходит в общий пропуск: следующий вызов с нормальным промптом на него пройдёт.

### Пример I — пара `tool_calls` ↔ `tool` должна ехать в одном чанке

Живой payload с настоящими tool_calls (20 КБ, `llm-ladder-tool-call-example.json`):

```json
{ "model": "service",
  "messages": [
    {"role":"system","content":"Ты — ассистент по разбору кода."},
    {"role":"user","content":"Посмотри файл и ответь словом: ок"},
    {"role":"assistant","content":"","tool_calls":[
      {"id":"call_probe_1","type":"function",
       "function":{"name":"read","arguments":"{\"path\":\"README.md\"}"}}]},
    {"role":"tool","tool_call_id":"call_probe_1","content":"# trained-assist-llm-ladder\n…"}
  ],
  "max_tokens": 40, "ladder_timeout_ms": 60000,
  "ladder_rung": "opencode-go/longcat-2.5-preview-free" }
```

| размер | результат |
|---|---|
| **4 740 байт** | ✅ ответил за **2.4 с** |

Отрицательный контроль: если `assistant.tool_calls` и его `role: "tool"` разнести по разным
чанкам, шлюз ответит `400 tool messages must include a non-empty string tool_call_id`. Пара
(`tool_call_id` ↔ `tool_calls[].id`) — минимальная единица чанкирования, её нельзя рвать.

### Пример J — живой инцидент: не влезает никуда → `every rung failed`

Сессия из инцидента 2026-10-08 (лестница `build`): payload вырос до **559 830 байт ≈ 128 948
токенов**, и отказала **каждая** ступень — по своей собственной причине:

```json
{ "model": "build",
  "messages": [ … 559 830 байт ≈ 128 948 токенов … ],
  "max_tokens": 32000, "ladder_timeout_ms": 60000 }
```

| ступень | результат |
|---|---|
| `opencode-go/longcat-2.5-preview-free` | ⏭ `input ~128948t above the rung ceiling` (потолок 100 000) |
| `zen-rings/nemotron-3-ultra-free` | ⛔ `559830 bytes, limit 50000` |
| `zen-rings/mimo-v2.6-flash-free` | ⛔ `559830 bytes, limit 20000` |
| `openrouter/inclusionai/ling-3.0-flash-sante:free` | в тот момент был в health-skip после апстрим-`429` |
| `openrouter/inclusionai/ling-3.0-flash`, `openrouter/xiaomi/mimo-v2.6-flash` | ⛔ `HTTP 402 Insufficient credits` |
| **итог** | ❌ `every rung failed` за **0.49 с**, вызывающий ретраит впустую |

Тот же запрос, когда ранг `ling-3.0-flash-sante:free` снова в обходе (его окно 262 144
вмещает и 128K, и 165K):

| размер | результат |
|---|---|
| **661 739 байт ≈ 165 419 токенов** | ✅ ответил за **9.3 с** на `build` |

Два вывода, которые и делают это ТЗ обязательным к исполнению:

1. **Отказ 0.49 с — это не поломка лестницы**, а честный отказ по размеру. Считать «что
   переполнилось» надо **до** отправки: `Buffer.byteLength(JSON.stringify(messages), 'utf8')`
   против лимита целевого ранга (§1). Локально это делает
   `npm run diagnose -- --ladder build --since 24h` — он печатает каждую ступень с её
   собственным лимитом и её собственным числом.
2. **Один временно пропущенный ранг лишает лестницу единственного места**, куда влезает
   жирный промпт, и дальше `every rung failed` каскадом. Отсюда требование к чанкеру: не
   полагаться на «где-нибудь влезет», а резать под **конкретный** лимит конкретного ранга.

## 5. Приёмка

1. На выборке ≥20 **жирных** сессий (источник: ТЗ по разметке, §2Е) доля `input is too long`
   и `above the rung ceiling` в ответах лестницы — **0 %**: всё чанковано до порога.
2. Ни один чанк не разрывает пару `tool_calls` ↔ `tool` (иначе `400 tool_call_id` —
   проверяется прогоном, а не чтением кода).
3. Средняя латентность ответа на чанке ≤ 15 с для бесплатного Go: если чанки упираются
   в 50 с (пример B) — значит чанк не маленький, а зен выбранный не для той задачи.
4. Никакой чанкер не превышает `messages` UTF-8 45 000 байт при цели «попасть в зен» —
   считается `Buffer.byteLength(JSON.stringify(messages), 'utf8')`, а не `.length`.
