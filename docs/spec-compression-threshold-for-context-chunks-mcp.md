# Порог сжатия для context-chunks-mcp и как его забенчить

Статус: расчёт на замерах 2026-10-08, живом проде и трассе за сутки. Решение — цифры ниже;
контракт с прокси — `COMPRESS_THRESHOLD` в `trained-assist/context-chunks-mcp`.

Компаньон: [spec-chunking-fat-prompts-for-free-tiers.md](./spec-chunking-fat-prompts-for-free-tiers.md) —
единицы, лимиты и примеры запросов.

---

## 1. Порог решает одну задачу: где лестница перестаёт быть надёжной

У лестницы три «потолка», и все три считаются в **байтах** `JSON.stringify(messages)`:

| граница | значение | что происходит дальше |
|---|---|---|
| гейт зена | **50 000 байт** (у `mimo-v2.6-flash-free` — 20 000) | зен уходит в гонку из 6 моделей |
| **потолок Go** | **100 000 токенов ≈ 400 000 байт** (`bytes/4`) | **бесплатного Go больше нет в обходе** |
| окна OR-free | 262 144 / 512 000 / 1 000 000 токенов | остаётся только OpenRouter `:free` |

Ниже потолка Go срабатывает **бесплатный и безлимитный** `opencode-go/longcat-2.5-preview-free`:
бенч на 39 жирных сессиях — **39/39 = 100 %**, медиана **7–11 с**, вход до 271 КБ (61K токенов).

Выше потолка Go лестнице остаётся только OpenRouter `:free`, и там всё совсем иначе.

## 2. Что происходит с жирными вызовами СЕЙЧАС (трасса за сутки, 4000 вызовов)

| метрика | значение |
|---|---|
| вызовов с признаком жирного входа (потолок Go / гейт зена / окно OR) | **445 (11,1 %)** |
| из них дошли до ответа | **322 = 72 %** |
| причины: гейт зена / потолок Go / окно OR | 800 / 542 / 43 попыток |
| по лестницам: `build` | **274/362 = 76 %** |
| по лестницам: `service` | **3/25 = 12 %** |

Гонка моделей в зене (запущена 08.10) дала в полосе >300 КБ **кумулятив 33 %** (7 из 21 гонки)
против 17 % на одну модель — помогает, но не спасает: отказы **скоррелированы по входу**
(батч 627 944 байт — все четыре модели упали подряд).

Побочные издержки жирного вызова, которые не видны в успешности:

- **health-skip'и чужих ступеней**: `503 Service temporarily overloaded` на 1M-ранге и
  `no first token in time` на sante выключали их для ВСЕХ вызывающих на 5 минут;
- **бюджет кольца**: одна гонка = до 6 задач из 500 суточных на (репозиторий, модель);
- **бюджет OpenRouter `:free`**: счётчик `free_model_daily_requests` (лимит 1000/сутки,
  замерено 355/1000 за сутки) — жирные вызовы едят его первыми.

## 3. Рекомендация: два порога — 350 КБ базовый, 100 КБ перед платной

```
COMPRESS_THRESHOLD               = 350_000 байт   # базовый: жирный вход, платный путь не предполагаем
COMPRESS_THRESHOLD_BEFORE_PAID   = 100_000 байт   # если запрос идёт к платной ступени
цель сжатого выхода              < 100_000 байт   (~25 000 токенов)
```

### 3.1 Первый порог — 350 КБ (базовый)

Почему **350 КБ, а не 50 КБ** (текущий дефолт прокси — `50000 chars`):

1. Ниже400 КБ лестница **надёжна**: бесплатный Go отвечает в 100 % случаев бенча за 7–11 с.
   Сжимать — значит добавить хоп, потерять детали и получить `get_context` ради экономии,
   которой нет (head-ранг `longcat-2.5-preview-free` — Free, unlimited, limited time).
2. Потолок считается как `bytes/4 > 100 000`, а реальный контур даёт **коэффициент 1.115**
   (298 988 против 268 116 при 1 072 461 байтах). Поэтому400 КБ — это уже граница, на которой
   запрос **может** быть отвергнут шлюзом: замер Go-шлюза — 392 КБ проходит, 491 КБ нет.
   **350 КБ даёт запас** (оценка 87.5K, реальный ≈97K токенов).
3. При целевом сжатии6.7× (замер на реальном запросе: 600 КБ → ~90 КБ) выход из350 КБ
   уходит в ~50–60 КБ — comfortably в зону Go. Даже при неудачном сжатии (1.5×) выход
   остаётся под потолком: 350 КБ / 1.5 = 233 КБ ≈ 58K токенов ✅.

Почему **не выше**500 КБ: чем ближе вход к потолку, тем вероятнее, что сжатый выход всё равно
останется выше него, и мы заплатим за сжатие зря (хоп + потеря деталей), а вызов уйдёт в
OR-зону с72 % успеха.

### 3.2 Второй порог — 100 КБ, когда платный путь предполагается

Бесплатный путь съедает вход до ~400 КБ (Go free), поэтому в базовом случае сжимать раньше
невыгодно. Но как только запрос **может уйти в платную ступень**, экономика меняется: платный
ранг ест месячную квоту (`mimo-v2.6-flash` $0.14/$0.28, `qwen3.7-plus` $0.40/$1.60,
`deepseek-v4-pro` $0.66/$1.98 за 1M), и чем тоньше вход — тем дешевле и быстрее.

Правило для прокси:

| условие | порог |
|---|---|
| `ladder_rung` явно называет **платную** модель | **100 000 байт** |
| `model` — лестница, у которой вызывающий ждёт качество и платный хвост (`doctor`, `service:gate`) | **100 000 байт** |
| всё остальное (интерактивные `build` / `plan` / `service` и т.п.) | **350 000 байт** |

Как определить «платную модель» в терминах лестницы: не `opencode-go/*-free` и не
`openrouter/*:free` (полный список рангов — `config/ladders.json`, тот же файл читает
`npm run embed-rungs`).

Почему именно100 КБ, а не ещё меньше: платный Go принимает до400 КБ, поэтому и на100 КБ
мы ничего не рискуем по доступности; зато сжатый выход (при6.7×) уходит в ~15 КБ —
это уже зона зена, где и латентность ниже. Дальше опускать порог бессмысленно: сжатие
платит деталями, а15 КБ и1 КБ одинаково дешёвы для ранга.

Для символов (если прокси не считает байты): **60 000 символов** = ~100 КБ в кириллице.

### Если прокси умеет считать только символы

Байты и символы расходятся: кириллица = 2 байта за символ, поэтому400 000 байт =
400 000 символов (ASCII) или **200 000 символов** (русский текст).

```
COMPRESS_THRESHOLD = 200_000 символов     # консервативно для кириллицы
```

Лучше всё же считать байты сериализованного `messages` — это ровно та величина, по которой
работают все потолки лестницы (`Buffer.byteLength(JSON.stringify(messages), 'utf8')`).

### Что НЕ сжимать

Ничего ниже **своего** порога (350 КБ или100 КБ — в зависимости от маршрута). В частности:

- промпты **< 50 000 байт** — зен и Go отвечают на них штатно;
- всё, что вызывается как `service:classify` / `service:format` с коротким вводом
  (трасса: `tokens_in` 6–10K — потолок в десятки раз выше);
- запросы, где вызывающий явно просит точность по содержимому файла целиком
  (сжатие отдаст сигнатуры, а `get_context` всё равно придётся звать).

## 4. Как забенчить: три слоя, от автоматического к ручному

### Слой 1 — размер/успех/латентность (полностью автоматически)

Существующий харнесс `scripts/fat-session-bench.mjs` уже умеет гонять **39 реальных жирных
сессий** через лестницу. Прогоняем их трижды:

| прогон | маршрут | что меряем |
|---|---|---|
| A | клиент → лестница (как сейчас) | ok-rate, p50/p90, число `input is too long` |
| B | клиент → **прокси (порог 350 КБ)** → лестница | то же + доля вызовов, ушедших в сжатие |
| C | клиент → прокси (**порог 200 КБ**) → лестница | то же — точка перегиба |
| D | клиент → прокси (база 350 КБ + **100 КБ перед платной**) → лестница | сколько вызовов и токенов ушло в ПЛАТНЫЕ ступени против прогона A |

Критерий: **B даёт ok-rate ≥ 95 %** и p50 не хуже, чем у A. Если C не даёт выигрыша в
ok-rate/латентности, порог не опускаем (сжатие без выгоды — это только риск потерять детали).

### Слой 2 — «агент работает?» (практика, без разметки)

Три метрики, которые видны в прокси без человеческой оценки:

1. **`get_context` на вызов** (0 / 1–2 / >3):
   - `0` на жирных вызовах — либо сжатие консервативно, либо агент не копал (проверить глазами
     на паре сессий);
   - `>3` — сжатие слишком агрессивное, агент вынужден распаковывать по частям;
   - **целевая полоса: 0–2**.
2. **Доля guard-отказов / пустых ответов** — сжатие не должно их увеличивать.
3. **Доля `input is too long` / `above the rung ceiling` после прокси** — должна упасть до ~0.

Всё это считается из уже существующих данных: трасса `ladder_calls.attempts` + счётчики
`get_context` в прокси.

### Слой 3 — качество ответа (ручной, один раз)

Автоматики для «правильности ответа» нет, и не строим её. Вместо этого:

1. Берём **10 вопросов из реальных жирных сессий** (то, что агент реально спрашивал) —
   они лежат в выгрузке `~/Downloads/fat-request-*.json` и в GCS-источнике из §2Е ТЗ.
2. К каждому — «эталонный» ответ из истории (агент уже ответил тогда, когда контекст был полным).
3. Прогоняем: полный контекст / сжатый (порог 350 КБ) / сжатый (200 КБ).
4. Сравниваем вручную один раз. Решение принимаем по **числу разборов по делу** (сжатый ответ
   упоминает нужные файлы/строки или нет), а не по стилю.

Этого хватает: сжатие детерминированное (без LLM), поэтому качество стабильно между прогонами —
одна ручная проверка10 вопросов переносится на весь корпус.

## 5. Приёмка

1. Пороги выставлены по **байтам** `JSON.stringify(messages)`: **350 КБ** базовый и **100 КБ**
   перед платной ступенью (или 200K / 60K символов, если прокси считает только символы).
2. Прогон D против A: число вызовов, дошедших до **платного** ранга, и суммарные `tokens_in`
   платных ступеней — должны упасть (цель: ≥ 50 % экономии на платной квоте).
3. Прогон A/B/C на39 сессиях: у B ok-rate ≥ 95 %, `input is too long` ≈ 0.
4. `get_context` на жирном вызове в полосе **0–2**.
5. Ручная проверка10 золотых вопросов: сжатый ответ не теряет ссылку на нужный файл/строку.
6. Счётчик `free_model_daily_requests` за день прогона вырос не более чем на число
   сжатых вызовов (то есть сжатие не породило лишних хопов).
