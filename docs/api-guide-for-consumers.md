# Как вызывать llm-ladder — гайд для нового потребителя

Базовый адрес: **`https://llm-ladder.trainedassist.store`**

Это OpenAI-совместимый шлюз: вы отправляете `POST /v1/chat/completions` с именем **лестницы**
вместо имени модели, а сервер сам идёт сверху вниз по списку моделей и отвечает первая, которая
сработала. Ломается одна — отвечает следующая. Вам не нужно знать, какие модели там стоят и в
каком они состоянии.

---

## 1. Авторизация

```
Authorization: Bearer <LADDER_TOKEN>
```

Токен выдаётся на клиента отдельно. Единственный эндпоинт **без** токена — `GET /health`.

**Как получить свой токен:** текущий держатель `LADDER_TOKEN` добавляет ваше значение
в переменную окружения воркера `LADDER_TOKENS` (через запятую, список нескольких
дополнительных клиентов) и выполняет деплой:

```bash
printf '%s' "$NEW_TOKEN" | npx wrangler secret put LADDER_TOKENS   # или правка в дашборде CF
```

Существующие `LADDER_TOKEN` и `LADDER_TOKEN_PREVIOUS` при этом остаются действующими —
выдача нового не ломает уже подключённых. Храните значение в секрете потребителя
(секрет-стор / Keychain / переменная окружения), **не в репозитории и не в логах**.

Ответ на неверный токен: `HTTP 401`.

---

## 2. Первый вызов

```bash
curl -s https://llm-ladder.trainedassist.store/v1/chat/completions \
  -H "Authorization: Bearer $LADDER_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
    "model": "service",
    "messages": [{"role": "user", "content": "Привет"}],
    "max_tokens": 200,
    "x-ladder-app": "my-app"
  }'
```

Ответ — стандартный `chat.completion`, поле `model` называет **ту модель, которая ответила**:

```json
{
  "id": "zen-rings-muxwx5lz-af3485a4",
  "model": "zen-rings/nemotron-3-ultra-free",
  "choices": [{"index": 0, "message": {"role": "assistant", "content": "…"}, "finish_reason": "stop"}],
  "usage": {"prompt_tokens": 22, "completion_tokens": 45}
}
```

Имя в `model` — это технический идентификатор ранга (`provider/модель`), он нужен вам только
для диагностики: «на чём ответило».

---

## 3. Какую лестницу выбрать

`model` = имя лестницы, не модели. Полный список отдаёт `GET /v1/models` (сейчас 30 штук).

| лестница | для чего |
|---|---|
| **`service`** | короткие сервисные вызовы: классификация, ответ кнопкой, форматирование, роутинг |
| **`build`** | основная рабочая лестница агента: правки кода, агентские ходы |
| **`plan` / `review` / `general` / `explore`** | те же роли отдельно (эксплор — под большой контекст) |
| **`free`** | **только бесплатные модели**, потолок в $0 — под тяжёлые тесты и нагрузку |
| **`conversation`** | генерация сообщений кандидату (hh-skill) |
| **`doctor`** / **`research`** | специализированные: сильные Go-модели / чтение и research |
| **`vision`** / **`vision advanced`** | мультимодальные (картинка + текст), стек Gemini |

У большинства лестниц есть **роли** вида `имя:роль` — `service:classify`, `research:explore`,
`doctor:plan`. Роль без суффикса (`build`) — дефолт для этой лестницы.

Одна лестница = один набор моделей. `service:build` и `service` — одно и то же.

---

## 4. Важная шапка: `x-ladder-app`

```http
x-ladder-app: my-app          # slug: [a-z0-9-], до 64 символов
x-ladder-app-title: My App    # человекочитаемое имя (необязательно)
```

**Отправляйте её всегда.** Она попадает в аналитику и единственная отличает ваши вызовы
от чужих в разрезе по приложениям (`GET /v1/analytics`). Если шапки нет, вызов помечается
`app = null`, и в отчёте он просто растворяется среди прочих — так сегодня выглядит
**4188 строк из 4190**.

Слаг, который не подходит под `[a-z0-9-]{1,64}`, не ломает вызов — он заменяется дефолтным.

## 5. Параметры вызова (необязательные поля тела)

| поле | по умолчанию | что делает |
|---|---|---|
| `ladder_timeout_ms` | `20000` | бюджет на один ранг (мс) |
| `ladder_ttfb_ms` | `15000` | при `stream: true` — окно до первого токена |
| `ladder_total_timeout_ms` | нет | бюджет на всю лестницу целиком |
| `ladder_rung` | — | пин на один конкретный ранг, **без** фейловера (для бенчмарков) |
| `ladder_conversation` | — | липкий ранг: следующий ход той же беседы пойдёт на ту же модель (сохраняет prompt-cache) |
| `stream` | `false` | `true` → SSE |
| `response_format` | — | `{ "type": "json_object" }` |
| `tools` | — | пробрасываются в модель как есть |

Ограничения, которые стоит знать:

- `ladder_rung` и `ladder_conversation` **взаимоисключающи** — пин делает выбор за вас.
- При `stream: true` после первого токена **фейловера нет**: ранг закреплён, дальше — только он.
- `ladder_total_timeout_ms` режет проход по лестнице: потрачен весь бюджет → в `attempts`
  появляется `skipped: time budget spent`, и вызов завершается.

## 6. Сколько ждать

Замеры на проде (не гарантия — это наблюдения, а не SLA):

| что | время |
|---|---|
| первый, быстрый ранг (бесплатный Go) отвечает | **4–14 с** |
| зен (если до него дошли) | **24–45 с** |
| рефол на холодном кольце | +10–13 с (однократно, следующий вызов уже тёплый) |
| мусорный вызов с промптом > порога | **0.4–0.6 с** — отказ до отправки |

Практическое правило: закладывайте **60 с** на не-стримовый вызов, если для вас важно получить
ответ, а не мгновенно упасть. Стрим начнёт отдавать данные раньше — первый токен обычно
приходит в первые секунды.

## 7. Ошибки — и что с ними делать

### `404 unknown ladder: <name>`

Имя лестницы написано неверно или больше не существует. Сверьте с `GET /v1/models`.
**Не ретрайте** — повтор даст то же самое.

### `401`

Неверный или отозванный токен. Проверьте заголовок и не попали ли вы в `LADDER_TOKEN_PREVIOUS`.

### `502 every rung failed`

Все лестницы отработали, ни одна не ответила:

```json
{
  "error": {
    "message": "every rung failed",
    "type": "ladder_error",
    "attempts": [
      {"model": "zen-rings/nemotron-3-ultra-free", "outcome": "error", "error": "…"},
      {"model": "opencode-go/longcat-2.5-preview-free", "outcome": "error", "error": "…"}
    ]
  }
}
```

Массив `attempts` — это и есть диагноз: какая модель пробовалась и почему не ответила.
Сохраните его в лог при репорте; без него «что-то упало» непроверяемо.

**Ретраить можно**, но с экспоненциальной паузой: лестница уже попыталась пройти весь список,
и немедленный повтор, скорее всего, упрётся в те же причины.

### `413` / `input is too long for the free tier: N bytes, limit M`

Промпт больше потолка конкретной модели. Сократите вход (историю диалога) — **не**
увеличивайте таймаут: сервер отвечает пустотой, а не отказом, и ожидание ничего не даёт.

---

## 8. Проверка, что всё живо

```bash
curl -s https://llm-ladder.trainedassist.store/health | jq
# → {"ok":true,"ladders":[…],"build":"<sha>"}

curl -s https://llm-ladder.trainedassist.store/v1/models -H "Authorization: Bearer $LADDER_TOKEN" | jq -r '.data[].id'
```

`/health` **не требует** токена — его можно вешать на uptime-проверку без хранения секрета.

Состояние здоровья рангов и ротации ключей: `GET /v1/state`. Свежая аналитика по лестницам,
моделям и ошибкам: `GET /v1/analytics?hours=24`.

---

## 9. Чего не делать

- **Не хардкодьте имя модели в `model`** — это имя лестницы. Модели внутри меняются, имена
  лестниц стабильны (их переименование — ломающее изменение и обновляется во всех клиентах).
- **Не шлите `x-ladder-app` с мусором** — она ваша идентичность в аналитике.
- **Не поднимайте `ladder_timeout_ms` до десятков секунд на всех вызовах** — это общая
  очередь. Длинное ожидание имеет смысл только там, где вам нужен ответ любой ценой.
- **Не логируйте токен** — ни в URL, ни в `attempts`, ни в телеметрию.
