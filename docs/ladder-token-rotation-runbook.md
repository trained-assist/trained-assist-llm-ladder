# Ротация ключа лестницы (`LADDER_TOKEN`) — runbook

Что за ключ, где он физически лежит, в каком порядке менять и как измерить, что ничего не сломалось.

---

## 1. Что это за ключ

`LADDER_TOKEN` — Bearer-токен, которым авторизуется **всё**, кроме `GET /health`.
Без него (или с чужим) воркер отвечает `401`.

| | |
|---|---|
| Где проверяется | `authorized()` в `src/handler.js` (~строка 172): сверка `Bearer` из заголовка с `env.LADDER_TOKEN`, constant-time |
| Где лежит истина | секрет воркера Cloudflare `LADDER_TOKEN` |
| Что идёт первым в запросе | `Authorization: Bearer <token>` |

Проверить ключ одной командой (значение **никогда не печатать**):

```bash
# 200 → ключ принят; 401 → отвергнут
curl -s -o /dev/null -w '%{http_code}\n' \
  -H "Authorization: Bearer $(cat ~/.llm-ladder-token)" \
  https://llm-ladder.trainedassist.store/v1/models
```

---

## 2. Карта мест, где он лежит

При ротации нужно пройти **все** строки. Пропущенная строка = тот клиент получает 401.

| # | Место | Что это | Как обновить |
|---|---|---|---|
| 1 | секрет воркера `LADDER_TOKEN` | истина в последней инстанции, Cloudflare Worker | `npx wrangler secret put LADDER_TOKEN` (перенаправить значение со stdin) |
| 2 | секрет воркера `LADDER_TOKEN_PREVIOUS` | **сейчас заявлена, но кодом не читается** — см. §3 | та же команда; смысл появится только после правки кода |
| 3 | org-секрет GitHub `LLM_LADDER_TOKEN` | его читают GH Actions-клиенты: `.github/workflows/collect-free-models.yml`, `pr-autofix.yml` (вход `llm_ladder_token`) | `gh secret set LLM_LADDER_TOKEN --org trained-assist` |
| 4 | `~/.llm-ladder-token` (chmod 600) | локальные скрипты: `npm run gate`, `scripts/go-usage.mjs`, `scripts/collect-free-models.mjs` | `printf '%s' "$T" > ~/.llm-ladder-token && chmod 600 ~/.llm-ladder-token` |
| 5 | `~/agent-tokens/llm-ladder/token` (chmod 600) | opencode-провайдер `ladder`: в `~/.config/opencode/opencode.json` (и `base.json`) прописано `provider.ladder.options.apiKey: {file:~/agent-tokens/llm-ladder/token}` | та же команда, что в строке 4 |
| 6 | VM с opencode | там, где лежит **своя** копия конфига opencode и своего файла токена | правка на самой VM |

Проверенный факт: строки 4 и 5 сегодня содержат **одно и то же значение** (совпадают sha256),
правятся синхронно. Строку 6 надо проверять отдельно — копия на VM может отставать.

**Клиентских репозиториев со своим секретом нет.** Проверено по API: у
`trained-assist-agent`, `pr-autofix`, `trained-assist-hh-skill`,
`software-engineering-playbooks` секрета с токеном лестницы не у ни одного — все они берут
org-секрет `LLM_LADDER_TOKEN` (строка 3). То есть клиентских репо обновлять нечего, кроме VM.

Переменные окружения у клиентов называются разно: скрипты читают `$LADDER_TOKEN`
(`scripts/live-gate.mjs`, `scripts/go-usage.mjs`) **или** `$LLM_LADDER_TOKEN`
(`scripts/collect-free-models.mjs`). Значение одно и то же, но прописано оно в двух разных
именах — если оно задано в окружении, менять надо оба.

## 3. Блокер: ротация сегодня — это катсвер

`authorized()` сверяет **только** с `env.LADDER_TOKEN`:

```js
// src/handler.js
function authorized(request, env) {
  if (!env.LADDER_TOKEN) return false;
  const token = bearerToken(request);
  return !!token && timingSafeEqual(token, env.LADDER_TOKEN);
}
```

Секрет `LADDER_TOKEN_PREVIOUS` существует в воркере, но **ни один файл его не читает**
(проверено грепом по репозиторию: 0 вхождений). То есть второй действующий ключ сейчас
невозможен, и порядок обновления принципиально не важен — в момент подмены секрета воркера
все клиенты со старым ключом получают 401 до тех пор, пока их не обновят.

Два практических следствия:

- **Нельзя** обновить клиентов «заранее» — они начнут слать новый ключ, а воркер ещё принимает старый.
- **Нельзя** обновить воркер «заранее» — старые клиенты начнут получать 401.

Поэтому «правильный» путь ротации (§5, Путь Б) предполагает сначала научить воркер принимать
**оба** ключа. Это ~3 строки и отдельная задача; без неё остаётся Путь А с измеримым окном.

## 4. Шаг 0 — собрать список живых клиентов (до любых действий)

Чтобы не пропустить строку в §2, сначала смотришь, кто реально ходит:

```bash
TOKEN=$(cat ~/.llm-ladder-token)

# кто вызывал за сутки (по x-ladder-app) + сколько осталось без заголовка
curl -s -H "Authorization: Bearer $TOKEN" \
  'https://llm-ladder.trainedassist.store/v1/analytics?hours=24' \
  | python3 -c 'import json,sys; d=json.load(sys.stdin); \
print("apps:");  [print("  ", a["app"], a["calls"]) for a in d["apps"]]; \
print("no_app:", d["no_app"]["calls"])'
```

`no_app.calls` — вызовы **без** `x-ladder-app`: это клиенты, которых аналитика не называет по имени,
но которые всё равно получат 401 при ротации. Их перечень дополняется грепом по клиентским
репозиториям (строки 5–6 §2).

## 5. Процедуры

### Путь А — сейчас, без правок кода (окно измеримое, но ненулевое)

Смысл: сузить окно до времени, за которое обновятся клиенты, и **измерить** его.

1. **Подготовить без изменений:**
   - сгенерировать новый токен: `openssl rand -hex 32` (не печатать, держать в переменной оболочки);
   - вывести чек-лист §2 и §4 в одну команду, чтобы не искать пути руками;
   - убедиться, что `npm run gate` зелёный **до** ротации — иначе после неё не отличишь сломанный ключ от сломанной лестницы.
2. **Обновить клиентов первыми** (строки §2: 3, 4, 5, 6). Начнутся 401 — это ожидаемо, окно открыто.
   ```bash
   T2=$(openssl rand -hex 32)                       # значение не печатать
   printf '%s' "$T2" | gh secret set LLM_LADDER_TOKEN --org trained-assist
   printf '%s' "$T2" > ~/.llm-ladder-token          && chmod 600 ~/.llm-ladder-token
   printf '%s' "$T2" > ~/agent-tokens/llm-ladder/token && chmod 600 ~/agent-tokens/llm-ladder/token
   # VM: продублировать два файла токена там же
   ```
3. **Обновить воркер** (закрывает окно для тех, кто уже обновился):
   ```bash
   printf '%s' "$T2" | npx --yes wrangler@4 secret put LADDER_TOKEN
   ```
4. **Замерить окно**: `end - start`, где `start` — момент шага 2, `end` — момент, когда
   `npm run gate` снова зелёный.
5. **Проверить:**
   ```bash
   npm run gate                 # 0 = зелёный
   npx wrangler secret list | grep LADDER_TOKEN   # обе строки на месте
   ```

### Путь Б — рекомендуемый (нулевое окно, требует правки кода)

Требует, чтобы `authorized()` принимал `LADDER_TOKEN` **или** `LADDER_TOKEN_PREVIOUS`. После этой
правки ротация выглядит так:

1. `LADDER_TOKEN_PREVIOUS` := текущий ключ (зафиксировать старый);
2. `LADDER_TOKEN` := новый ключ — **оба приняты, окна нет**;
3. обновлять клиентов §2 в спокойном темпе (можно часами), отслеживая остаток непереключённых по
   `/v1/analytics` и по `401` в логах;
4. убедиться, что остаток нулевой, и удалить `LADDER_TOKEN_PREVIOUS`
   (`npx wrangler secret delete LADDER_TOKEN_PREVIOUS`).

Это **правка в access-control-слое** — входит в п.3 плана («перепишём надёжно и измеримо»),
в п.1 по задаче она не входит.

---

## 6. Правила

- Значение ключа не попадает в репозиторий, в промпт, в лог и в артефакты — только в секреты и
  в `~/.llm-ladder-token` с правами 600.
- `npm run gate` до и после любой ротации: до — чтобы был зелёный ориентир, после — чтобы
  подтвердить, что 401 не осталось.
- Ротация ключа **не** является поводом трогать `config/ladders.json`: порядок ступеней и авторизация
  независимы.
- Прочие ключи воркера (`ZEN_RUNNER_TOKEN`, `ZEN_RING_ADMIN_TOKEN`, `POOL_TRIGGER_TOKEN`,
  `OPENCODE_ZEN_RELAY_TOKEN`) — отдельные поверхности со своими роутами и **не** входят в эту
  процедуру. Если нужна их ротация — это отдельный runbook.

---

## 7. Связанные задачи

- Путь Б из §5 (принимать `LADDER_TOKEN_PREVIOUS`) — prerequisite нулевой-оконной ротации.
- Разделение репозиториев (приватное ноу-хау zen-rings против открытой лестницы) — ротация ключа
  после переезда меняет только строку 1–2 §2, остальной чек-лист не зависит от того, в каком репо
  лежит диспетчер.
