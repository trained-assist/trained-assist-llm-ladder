# ТЗ: разметка промптов по «толщине» и где брать жирные данные

Задача: разметить промпты меткой вида **«этот — 60 % толстых, а этот — 10 %»** и знать, откуда
брать жирные промпты для стендов и бенчмарков.

Статус: ТЗ. Все числа ниже — замеры 2026-10-08, не оценки.

---

## 1. Метрика: толщина промпта

Толщина — **доля payload-а, которую занимает НЕ пользовательский текст**:

```
fat% = (байты tool-сообщений + байты tool_calls внутри assistant + байты assistant)
       ─────────────────────────────────────────────────────────────────────────
                          байты всех messages
```

Почему так, а не «просто размер»: размер даёт шум (системный промпт opencode сам весит
50–121 КБ), а доля tool-контента показывает, что именно раздуло запрос — выводы инструментов
против текста пользователя.

Две вспомогательные метрики, которые тоже нужны в отчёте:

| метрика | зачем |
|---|---|
| `size_bytes` / `size_tokens` | абсолютный размер (токены ≈ `bytes / 3.0–3.5`, см. §4) |
| `n_messages` | сколько реплики в истории: 2 vs 860 — это разные виды жирности |

### Шкала разметки

| метка | диапазон | что это |
|---|---|---|
| **тонкий** | `fat% < 10` | system + user, истории нет |
| **средний** | `10 ≤ fat% < 40` | немного реплик ассистента |
| **толстый** | `40 ≤ fat% < 70` | смешанная история |
| **очень толстый** | `fat% ≥ 70` | история целиком из выводов инструментов |

### Реальные примеры для калибровки (замерено, не выдумано)

| источник | байт | сообщ. | **fat%** | разбивка | метка |
|---|---|---|---|---|---|
| продовый промпт | 35 721 | 3 | **0 %** | user=33520, system=2213 | тонкий |
| продовый промпт | 122 349 | 2 | **0 %** | system=121148, user=1211 | тонкий (но огромный system!) |
| продовый промпт | ~200 625 | 64 | **81 %** | tool=82788, assistant=75249, tool_calls=24805 | очень толстый |
| продовый промпт | ~299 377 | 92 | **86 %** | tool=187890, assistant=65632, tool_calls=24524 | очень толстый |
| `conversation-bench-data` (рекрутинг) | 2 317–9 017 | 2 | **0 %** | system=1 %, user=99 % | тонкий |

**Калибровочная точка для «10 %» и «60 %»:**

- **10 %** — это не fat% отдельного промпта, а **доля толстых промптов в потоке**:
  из 5914 payload-ов tool-контент есть только в **573 (9.7 %)**. То есть «один из десяти».
- **60 %** — середина между наблюдаемыми полюсами (0 % и 81–86 %); в нашей выборке
  промптов с fat% 40–70 почти нет — распределение **бинарное**: либо system+user,
  либо почти вся история из tool.

## 2. Откуда брать жирные промпты

### А. Прод — `zen_pool_tasks.messages` (основной источник)

Что реально уходило в лестницу. База: Cloudflare D1 **`trained-assist-llm-ladder-trace`**
(uuid `e26b1e9d-c1ad-4bf6-bcf5-3ebcb8eaf92e`; `ZEN_DB` указывает туда же — см. #156).

> **Доступ:** локально `wrangler d1 execute` не сработает — в `wrangler.toml` у биндингов
> заглушка `database_id = "00000000-…"`, а wrangler идёт по id. Нужен конфиг с настоящим uuid
> (или доступ к CF из соседней сессии).

```sql
-- распределение по размеру
SELECT CASE WHEN length(messages)<5000 THEN '<5KB' WHEN length(messages)<20000 THEN '5-20KB'
            WHEN length(messages)<50000 THEN '20-50KB' ELSE '>50KB' END AS b, COUNT(*)
FROM zen_pool_tasks GROUP BY b;

-- payload-ы с tool-контентом (кандидаты на «толстые»)
SELECT model, length(messages) AS bytes, messages FROM zen_pool_tasks
WHERE messages LIKE '%"role":"tool"%' ORDER BY length(messages) DESC LIMIT 20;
```

**Свойства:** 5914 payload-ов; tool-контент в 573 (9.7 %); размеры `<5 КБ` … `≥1 МБ`;
успех по размеру 51–62 % ниже 50 КБ и **15–19 % выше**.

## 4. Байты против токенов

Для LLM важны **токены**, но в замерах `zen_pool_tasks` байты — хороший проводник:
на 3408 парах `(bytes, prompt_tokens)` корреляция Пирсона **0.981**.

| размер | байт на токен (p50) |
|---|---|
| 0–2 КБ | 2.05 |
| 2–10 КБ | 2.74 |
| 10–40 КБ | 3.10 |
| >40 КБ | **3.46** |

Зависимость **почти линейная, но коэффициент растёт с размером**: мелкий текст токенизируется
плотнее (≈2 байта/токен), крупный — разреженнее (≈3.5). Отсюда практические следствия:

- оценка `len / 4` в `estimateTokens` — **пессимистичная** (занижает токены), что безопасно:
  завышенный потолок лишь чуть раньше откажет;
- байтовый порог `ZEN_MAX_INPUT_BYTES = 50 000` — это **~14–17K токенов**, а не 12.5K;
- если метку считать в токенах, делить нужно на **3.0–3.5**, а не на 4.

## 5. Приёмка

1. Скрипт разметки выдаёт на вход пул промптов и возвращает `(id, size_bytes, size_tokens,
   n_messages, fat%, label)` по шкале §1.
2. На выборке ≥200 промптов распределение меток воспроизводит наблюдаемую бинарность
   (≈90 % «тонкий», ≈10 % «очень толстый») — если вылезло много «средних», метрика ошибается.
3. Жирные промпты для стенда берутся из §2А (прод) или §2Б (наша переписка), **не** из §2В —
   рекрутинговый корпус тонкий, и обманывать себя им нельзя.
